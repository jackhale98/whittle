# M4.1 design: closing the 16 drawing pick gaps

> Design for PLAN M4.1 (2026-11-12). The contract changes below landed in 48a9b01 (ADR-095); rp04 and rp10 take the recommended spec-side option. Workstreams A (kernel), B (modeling), C (drawing/web), then D (fixtures and certification driver).

I read the code only (no runs). A short contract change, one small kernel change, and three parallel workstreams close all 16 gaps. Two gaps need a spec-side decision: rp04 `boss_up` and rp10 `slot_x0`. One gap is probably misdiagnosed: rp07 `inset` (see HIDDEN).

## Contract diff (lead commit, before branching; SCHEMA_VERSION stays 4)

All of these are additive. Only the `RefPoint` union is a stored type, and it only widens.

```ts
// packages/contracts/src/drawing.ts — ProjectedCurve, after `face`:
  /**
   * M4.1, section views: this curve is an edge of a cut face (it lies on the cutting surface). The
   * value is the persistent name of the model face the cut passes through along it: the cut
   * face's other neighbour in the cut result. A pick on it refs that face (`kind: 'face'`), so a
   * dimension between cut edges measures model faces and re-resolves like any face ref. Absent on
   * steps between two cut segments, and wherever that neighbour is not exactly one model face.
   */
  cutFace?: string;

// packages/contracts/src/annotation.ts
/**
 * …existing text…
 * `min` / `max` (M4.1): the entity's extreme point along the dimension's `direction`. Only for
 * linear and ordinate dimensions that have a direction: a circle's, cylinder's or sphere's tangent
 * point, a line's lower or upper end. A diameter in linear form is refs [c, c], at ['min', 'max'].
 * `axis` on a planar face, in an angle: the face's normal (the pull direction a draft is measured from).
 */
export type RefPoint = 'self' | 'center' | 'axis' | 'start' | 'end' | 'mid' | 'min' | 'max';
// AnnotationBase.refs doc, add: "Construction refs (M4.1), drawn on a view as thin chain lines
// once a placement there uses them: `origin:O`, `origin:X|Y|Z`, `S<id>:p(@origin)`,
// `S<id>:e(@x|@y)`, `S<id>:p(<point>)`, `F<id>:plane|axis|point`, and `F<pattern>:pitch` (the
// pitch circle of a circular pattern of holes)."
// AngleDimension doc, add: "A draft angle is refs [drafted face, neutral face], at ['self', 'axis']."

// packages/contracts/src/modeling.ts — AnnotationAnchor, add:
  /** M4.1: a torus face (a fillet at a shaft step) for radius dimensions. The layout uses the
   *  meridian circle (radius `minor`) seen face-on in the view, on the side the leader points to. */
  | { kind: 'torus'; center: Vec3; axis: Vec3; major: number; minor: number }
// AnchorQuery.annotationKind doc: "`radius` on a torus face gives a `torus` anchor."
```

The lead also makes these changes in the same commit:
- **packages/document:** add `'min'` and `'max'` to `REF_POINTS` (`annotations.ts`). Add a rule in `annotation-rules.ts`: min/max only on linear or ordinate dimensions with a `direction`, else `refsDoNotFit`. Add tests.
- **docs:** ADR-095 in DECISIONS.md.

There is no change to `ViewBase`, so no persisted per-view "show sketch" list. Construction geometry is drawn when an annotation on the view uses it. While a picking tool is active, it is shown as transient pick targets. An explicit `ViewBase.construction?: Id[]` can come later.

## Per gap class: (a) why it fails, (b) contract, (c) kernel, (d) what is stored, (e) tests

### CONSTRUCTION (rp03 flat_h, rp08 cs_x/cs_y, rp09 pcd, rp10 slot_x0, rp04 boss_up)

**(a) Why it fails**
- `compose.ts` draws only `proj.curves`, automatic centre marks on full arcs, and manual CenterMarks. `interact.ts edgeAt` returns null for a view item with no `edge` and no `face`. So nothing on a centre line can be picked.
- Nothing in `apps/web` queries `S:p(@origin)` or `S:e(@x|@y)` for display.
- `refGeometry` (kernel-client `annotations.ts:696`) has no name for a pitch circle.
- `ORIGIN_AXES` resolve with `extent: [0, 0]`, so their anchors have zero length.

**(b) Contract:** names and docs only (above).

**(c) Kernel:** none. The anchors come from `annotationAnchors` and are projected in TS.

**(d) What is stored**
- The annotation stores the exact construction name that was drawn under the pointer, e.g. `{ name: 'origin:Y', kind: 'edge' }` or `{ name: 'F<ring>:pitch', kind: 'edge' }`.
- The resolver already handles origin, sketch, plane, axis and point names. A deleted or failed source is needs attention; a suppressed one is "not in this configuration".
- New name `F<p>:pitch`, resolved by the modeling stream:
  - circle about `p.axis` as it resolves in the final state;
  - radius = distance from that axis to the walls of the hole instances (`holeInstances`); every instance must be at the same distance within tolerance;
  - centre on the axis at the original instance's entry level.
  - If the sources are not holes, or the radii differ, it is unresolved with an `error`. It is never guessed.
- Candidates shown while picking:
  - Built by a pure `constructionQueries(part)` in packages/drawing: origin O/X/Y/Z, each sketch's `@origin`, `@x` and `@y`, its standalone points (construction points, or points that are not curve ends or centres), plane/axis/point features, and circular patterns.
  - One `annotationAnchors` call per `ConfigData.make` (memoised per regen result, made before the slot closes).
  - Projected per view. Lines seen end-on and planes not seen edge-on are skipped. Lines are spanned to the view's part bounds plus 3 mm.
  - Coincident candidates are deduped by a fixed priority (origin, then history order). This is a UI rule over exact names, not a topological guess.
  - Model edges outrank construction items in a hit.
- Used construction refs are drawn by `compose` from the resolution anchors: role `center`, `ItemSource.view.construction = name`. If the ref is unresolved, nothing is drawn.

**rp04 boss_up: not achievable without inventing a level.** The push/pull has no sketch plane, and no face of the finished part is at z = 36. Two spec-side options:
- **Recommended:** the builder adds a reference plane `boss_lvl`, offset `plate_t + boss_h - boss_up` from XY. `boss_up` is then dimensioned from `F{boss_lvl}:plane` (edge-on) to the boss top. Measured value 6, and it re-resolves.
- **Alternative:** drop `boss_up` from the spec drawing (93/93). Needs the owner's sign-off.
- A history construction name such as `F<pull>:from(…)`, drawn as an ISO 128 phantom line, would be honest too, but it is niche. Defer it.

**rp10 slot_x0:** the finished part has no slot-centre entity. Recommended spec-side fix: add a construction centre point `SC` at (`slot_x0`, 0) to `slot_sk`. The dimension is then `origin:Y` ↔ `S{slot_sk}:p(SC)`. A median-plane ref (rejected in ADR-094) or a midpoint snap are the alternatives.

**Small modeling-stream fix:** give origin axes a span like sketch axes (the bounds of the bodies), so extension feet sit on the part.

**(e) Tests**
- kernel-client goldens:
  - `F<ring>:pitch` on rp09 = Ø90;
  - the `pcd` stage edit updates it;
  - deleting the pattern makes it unresolved with cause `deleted`; suppressing it gives `suppressed`;
  - a pattern of non-holes gives an error;
  - origin-axis spans;
  - rp03 `origin:X` ↔ flat edge = 18;
  - rp08 `origin:Y` / `origin:X` ↔ countersink rim centre = 30 / 18.
- drawing unit tests: candidate dedupe and priority, end-on skip, compose draws used refs only.
- web unit tests: a construction pick gives an `EdgePick`, and `planDimension` stores the name.
- E2E: certification rows, plus an edit-upstream check (change `pcd`, the value follows; delete the sketch, needs attention).

### SECTION (rp05 wall, draft_a; rp08 tap_depth; rp09 hub_h)

**(a) Why it fails**
- In `cutForSection` (`wren_drawing_hlr.cpp:701`), edges map back only through `bop.Modified`. The new cut edges get `edgeOrigin = −1`, so `decode.ts` leaves them unnamed and `edgeAt` returns null.
- Coincident model edges behind the cut (far corners, half-rims) are numerically ambiguous in HLR.
- Even once pickable, `wall` would be wrong. `planDimension` snaps to an axis when `|n·x| > 0.98`. The walls are drafted 3° (cos 3° = 0.9986), so it sets `direction` = horizontal. With a direction, `measuringPoint(plane)` is the face centroid, so the value is not 3.
- `draft_a`: the driver's `dimensionTool` has no angle path, and nothing refs "the vertical".

**(b) Contract:** `ProjectedCurve.cutFace`, plus the RefPoint doc for `axis` on a plane in an angle.

**(c) Kernel (small; only in `wren_drawing_hlr.cpp`)**
- After the cut, run `MapShapesAndAncestors(result, EDGE, FACE)`.
- For each edge of a `cut.faces` face: if it has exactly two ancestors, and the one that is not a cut face has `faceOrigin ≥ 0`, then `cutFace = faceOrigin`. Otherwise −1. Two cut faces (a step) give −1.
- Thread a `CutFaceOf` callback, like `EdgeOrigin`, through `runExact` (with the same `NewSOldS` fallback), `runDraft` and the `slice` loop.
- JSON: each curve gets `"cutFace": int`.
- `decode.ts`: map it through `faceNames`. An index past the names is INTERNAL; −1 leaves the field absent.
- Salt the projection key so cached projections without `cutFace` are not reused.

**(d) What is stored and how it resolves**
- A cut pick is `EdgePick { name: cutFace, ref: 'face', cut }`. Refs are model faces at `'self'`. For linear dimensions these already resolve plane-like (ADR-090 amendment), with rebound or merged handling and needs attention when gone.
- Two cut lines of the same face that are parallel and not collinear are that cylinder's diameter. Collinear lines of one face are refused.
- In `planDimension`, set `direction` (and the lane) only when the edges are exactly axis-aligned (1e-6). Otherwise use the natural separation with an `offset` layout. Then `wall` = 3, normal to the walls (spec: "measured normal").
- `draft_a`: Angle tool, pick the drafted wall's cut edge, then the bottom's cut edge, then switch on "From the normal of the second face" (the inspector, or Shift on the second pick). The angle is refs [`F{base}:side(…L2)` as drafted, `F{base}:start`], at ['self', 'axis'], value 3°.
  - kernel-client: `angleBetween` treats a plane at `axis` as a line along its normal, and skips the kernel `measureShapes` path for it.
  - Layout: the vertex is where the two edge-on lines meet (the base corner); the second leg runs along the projected normal, on the wall's side.
  - Optional: Import promotes the Draft feature's `/angle` with these refs.
- hitTest: at equal distance, prefer the `cut` item over a coincident model edge.

**(e) Tests**
- kernel golden `drawing-section-names.golden.test.ts`: a box with a blind flat-bottomed hole, cut through the hole's axis. Every cut-face boundary curve names the expected face (top, both hole walls on one cylinder, bottom, sides). A stepped cut's step edges have none. Exact, draft and slice. Plus a decode unit test.
- kernel-client goldens:
  - rp05 drafted faces: natural separation = 3, stage 2 = 4;
  - draft angle = 3°, stage 3 = 5°;
  - rp09 planes 30, rp08 planes 12.
- drawing: the angle layout's vertex and normal leg.
- web: cut-edge picks give face refs, the exact-alignment rule, same-face diameter.
- E2E: the four certification rows, plus the rp05 stage edit.

### TOOL-CENTRES (rp08 tap_dx)

- **(a)** In `interact.ts onPick`, case `'dimension'` calls `createDimension` on the first circle pick.
- **(b)** None. **(c)** None.
- **(d)** The first circle pick now sets the hint "Pick a second edge or circle, or the same circle again for its diameter (Alt: radius)". The existing `ca && cb` branch stores at ['center', 'center'] with direction x or y.
- **(e)** web unit tests: the tool waits; same circle gives a diameter; Alt gives a radius; two circles give a centre distance; a sphere outline still works. Update the existing m4-drawings and m4-touch E2E steps that click a circle once.

### OUTLINE-SPLINE (rp02 fillet_r)

**(a) Why it fails**
- `pickEdge` returns `shape: 'other'` for a B-spline, and `onPick` toasts "That edge is curved".
- `subGeometry`/`exactFace` has no torus, so the face is `'other'` and gives "not round".
- `test-hooks edges()` lists only lines and arcs.

**(b) Contract:** the `torus` anchor.

**(c) Kernel:** none. `subShapeGeometry` already returns torus data.

**(d)** A one-pick radius on a face-named outline that is not an arc:
1. Ask `annotationAnchors({ ref: face, annotationKind: 'radius' })`.
2. If the anchor is a torus, circle or sphere, store the radius on that face (`F<fillet>:fillet(…)`). Otherwise refuse with the reason.
3. kernel-client: `RefGeo` gets `torus`. Radius = minor radius. The radius anchor is the `torus` anchor.
4. Layout: when the axis lies in the view plane, the two meridians are at centre ± major across the axis. Pick the one on the side of `layout.angle`: deterministic from the stored placement.

**(e) Tests**
- kernel-client: radius on a torus = 3 and follows `fillet_r` edits.
- drawing: the layout chooses the meridian side.
- web: a spline outline pick gives a radius; a non-round face is refused.
- E2E: rp02.

### TANGENT (rp06 rod_h, rod_tail)

- **(a)** `tangentEdges` defaults to `'off'` (`style.ts:38/69`, `solve.ts:92`). So `projectionRequest` sends `smooth: false` and the façade skips HLR types 3 and 4: no curve at the bend.
- **(b)** None. **(c)** None.
- **(d)** Product picking already works once the edges are drawn: smooth edges are named and visible, and role `tangent` is hit. Refs are model edges. `rod_h` = plate edge ↔ the tangent circle seen edge-on (measured at its centre) = 20.
- The fix is the spec plus the driver: `DrawingViewSpec.display?: { hidden?: boolean; tangent?: 'thin' | 'visible' }`, applied through the ViewInspector. Do not change the default (it would churn every golden).
- **(e)** E2E for rp06. A web unit test that a tangent item gives a pick.

### HIDDEN (rp07 inset): probably misdiagnosed

**(a) Why it fails**
- Product: `pickEdge` and `test-hooks edges()` keep only `role === 'visible'`, and the default `lines` is `'visible'`.
- Geometry: the loft narrows upward, from 50×30 at z = 10 to 30×14 at z = 50. Its base edges therefore face up and should be visible from +Z. The spec SVG draws them dashed.
- The more likely miss is in the driver. The spec point (−25, 30) is 15 mm past the inset edge's end at (−25, ±15), beyond `SLACK` (3.5).
- Confirm with `WREN_CERT_ALL=1` and the `projection()` roles before building anything.

**(b)** None. **(c)** None.

**(d)** Build these cheap product changes anyway:
- `pickEdge` accepts hidden runs when the view shows hidden lines, preferring visible ones;
- the hooks list hidden curves with their `role`;
- hitTest prefers visible over hidden at equal distance.

The driver gains an extension fallback: a straight line within 5° of perpendicular to the measured axis whose infinite line passes within TOL of the spec point, nearest along the line. rp03 (x = 31), rp05 `wall` and rp08 `tap_depth` need it too. If the edge is visible, correct the spec SVG and note it in the README.

**(e)** Unit tests for hidden picks and the tie-break. E2E for rp07.

### EXTREMES (rp09 flange_d)

**(a) Why it fails**
- No RefPoint names a tangent extreme. `measuringPoint(circle, self)` is the centre, so [c, c] measures 0.
- The driver finds no edge at (−60, −60), and the tool can only make a diameter.

**(b)** `RefPoint` `'min'` / `'max'`. **(c)** None.

**(d) What is stored:** linear, refs [rim, rim], at ['min', 'max'], `direction` = the view's x.
- kernel-client: measure the extreme points of circles, cylinders, spheres and lines along `direction`. Plane at min/max is unmeasurable, with a reason.
- Layout: the extension feet are at the extremes.
- UI:
  - the diameter inspector gets "Form: Ø / ↔ linear across / ↕ linear across" (`updateAnnotation` with the same id plus `updatePlacement`, one coalesce key, one undo step);
  - Shift on the second pick of the same circle does the same.

**(e) Tests**
- kernel-client: 120 across the rim; a sphere; a cylinder face; the validator refuses min/max without a direction.
- Layout goldens.
- An inspector unit test.
- E2E for rp09.
- The suite gains a kind check: spec `linear` must be a linear, aligned or ordinate annotation. Today a Ø120 diameter would count as met.
