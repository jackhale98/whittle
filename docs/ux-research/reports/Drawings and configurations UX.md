# Make configurations explicit and drawings exact

Across SolidWorks, Onshape, Fusion, Creo, NX, FreeCAD and Shapr3D, users lose the most work in configurations and drawings for the same reason: **the software does something they cannot see**. With configurations, an edit lands on the wrong variant because the edit scope is a hidden setting that has flipped from "this" to "all" ([SW forum 243322](https://forum.solidworks.com/thread/243322)). With drawings, a dimension shows a value that is no longer anchored to anything; Fusion users say the drawing "will happily give you an incorrect dimension" ([Autodesk forum](https://forums.autodesk.com/t5/fusion-support/drawing-dimensions-are-incorrect/m-p/12021471)). In both milestones, Wren's main design job is to make state visible. For M3.7 that means a sparse "default plus overrides" model keyed by id, edit scope shown at the field being edited, override markers, and per-configuration rebuild status computed in the worker. For M4 it means a drawing whose dimensions are either correct or flagged as "needs attention", never silently stale, built on data-bound templates and edited without a separate modal format mode. The praised workflows are cheap to copy: Onshape's click-to-configure fields, Fusion's rule that unconfigured edits apply everywhere, SolidWorks' even-spacing dimension placement, Onshape's propagating hole callouts, and Shapr3D's tap-to-project menu. Exports follow from one rule: **sheet millimetres all the way down**. The PDF MediaBox equals the sheet, mm are converted to pt exactly once, and print scaling is set to None, backed by a printed 100 mm scale bar because viewers ignore the flag. SVG uses one user unit per mm. DXF defaults to R2000 with `$INSUNITS` set and one layer per line role, plus an R12 "lines and arcs" profile for laser and CNC, because splines are the most common reason shops reject DXF files. Wren's own architecture matters here. M3.5 added exact sketch B-splines and elliptic arcs (`docs/DECISIONS.md` ADR-056), so its drawings will contain the curve types CAM tools reject. QCAD's command-line converters are commercial ([QCAD](https://qcad.org/en/qcad-command-line-tools)), so the "opens in QCAD" acceptance criterion needs an owner decision rather than an assumed CI job.

## Edit scope ambiguity, not missing features, is what breaks configurations

### Every mature tool converges on a default plus overrides

The tools split into two families. **Table-of-variants** tools store one row per named variant: SolidWorks design tables and the Modify Configurations grid ([SW Help 2020](https://help.solidworks.com/2020/English/SolidWorks/sldworks/r_modify_configurations_dialog.htm)), Creo family tables with a generic and its instances ([PTC Creo 9 Help](https://support.ptc.com/help/creo/creo_pma/r9.0/usascii/fundamentals/fundamentals/About_Instance_Operations.html)), NX part families, and FreeCAD's spreadsheet configuration tables with variant links ([FreeCAD wiki](https://wiki.freecad.org/Variant_link)). **Input-driven** tools define typed inputs and treat a variant as a combination of input values. Onshape offers a List (named rows whose first row is Default), a Checkbox, and a typed configuration variable (`#name`) with default, minimum and maximum ([Onshape Help](https://cad.onshape.com/help/Content/PartStudio/part_studio_and_assembly_configurations.htm)). Underneath, both families share one structure: a default, a set of configured values that differ per variant, and unconfigured values shared by all variants. Fusion, which shipped configurations in September 2023 ([Fusion blog](https://autodesk.com/products/fusion-360/blog/september-2023-product-update-whats-new)), states the rule most cleanly: **editing an unconfigured aspect affects every configuration, and editing a configured aspect affects only the active one** ([Fusion Help](https://help.autodesk.com/cloudhelp/ENU/Fusion-Configurations/files/CFG-OVERVIEW.htm)). Fusion also shows how to stop the table growing too wide. Its "theme tables" group material, appearance and rules beneath a narrow top table ([Fusion Help](https://help.autodesk.com/cloudhelp/ENU/Fusion-Configurations/files/CFG-OVERVIEW.htm)), and Wren can get the same effect from collapsible column groups.

PLAN M3.7 already describes a table-of-variants model: named configurations that set parameter values, suppression, material and custom properties over a default. The evidence supports storing each configuration as **sparse overrides keyed by stable id**, so that any cell without an override inherits the default. This has the same shape as SolidWorks' "linked vs overridden" derived configurations and Fusion's "configured vs unconfigured aspect". It also maps directly onto the per-(configuration, parameter) merge conflict that PLAN M3.7 specifies.

Two details in Wren's current contracts make this harder than the PLAN wording suggests. First, `Param` is document-level (`packages/contracts/src/document.ts`, `WrenDoc.params`), but configurations belong to a part. A part configuration that overrides a global parameter therefore needs a defined scope. The safe default is that the override applies only while that part is regenerated. Second, many values users configure in practice are feature fields, not named parameters. The commonest example is fastener families, such as FreeCAD's M10/M12 nut variants ([FreeCAD wiki](https://wiki.freecad.org/Variant_link)). In Wren, `HoleFeature.size` and `kind` are enums, not `Expr` values. Onshape and Fusion both configure feature parameters directly ([Onshape Help](https://cad.onshape.com/help/Content/PartStudio/part_studio_and_assembly_configurations.htm); [Fusion Help](https://help.autodesk.com/cloudhelp/ENU/Fusion-Configurations/files/CFG-CONFIGURATIONS.htm)). An override key of the form `(featureId, fieldPath)`, alongside `paramId`, would cover these cases without a second mechanism. That is a contract change for the lead.

### Users lose work to invisible scope, silent suppression and quiet reverts

The complaints rank clearly. **Scope ambiguity comes first.** A SolidWorks user found that an equation set to "This Configuration" had flipped to "All Configurations", so later edits silently changed every variant ([SW forum 243322](https://forum.solidworks.com/thread/243322)). SolidWorks' own example shows that "This Configuration" on a parent also changes its derived children ([SW Help 2012](https://help.solidworks.com/2012/English/SolidWorks/Sldworks/Example_of_Derived_Configurations.htm)). The vendor's tech blog runs a post titled "Confusing SOLIDWORKS Configurations?" ([SOLIDWORKS Tech Blog](https://blogs.solidworks.com/tech/2017/04/confusing-solidworks-configurations.html)). An Onshape user with nested configurations says it is "difficult to tell what a change will affect" ([Onshape forum](https://forum.onshape.com/discussion/comment/125960)). The lesson is that scope must be visible **at the point of edit and after the fact**, not stored in a sticky flyout setting, and that derived (nested) configurations multiply the ambiguity. Wren should leave them out of M3.7.

**Suppression traps come second.** A SolidWorks configuration option suppresses newly added features and mates in all other configurations, which makes mates "disappear" when the user switches ([CATI](https://www.cati.com/?p=119967)). In Onshape, switching to a configuration that suppresses a part breaks a downstream extrude whose merge scope referenced that part ([Onshape forum 29547](https://forum.onshape.com/discussion/29547/unexpected-behavior-advanced-configuration-workflows-exercise-configuring-multi-part-part-studios)). Fusion's own best practice is that if suppression is configured at all, every suppression state goes into the table ([Fusion Help](https://help.autodesk.com/cloudhelp/ENU/Fusion-Configurations/files/CFG-OVERVIEW.htm)). Wren's golden rule already says what to do with that Onshape break: a reference that resolves in the default but not in configuration B is "needs attention" **for B only**, and the message names the suppressed feature as the cause. That second part follows the earlier finding that users want errors reported at their upstream cause.

**Quiet reverts come third, and they are the configuration form of "silently guessing a reference".** SolidWorks users report components switching configuration on their own ([SW forum 233493](https://forum.solidworks.com/thread/233493)). On 3DEXPERIENCE, a part in an assembly reverted to the first available configuration when it was already cached, and saving made the change permanent ([r/SolidWorks mirror](https://redlib.ssps.io/r/SolidWorks/duplicates/1g7d4xd)). The equivalent rule for Wren: a drawing view, BOM or (in M6) assembly instance that stores a configuration id that no longer exists **must not fall back to Default**. It is flagged.

**Staleness and cost come last.** Creo reports each instance's verification state: never verified, generic changed since the last verify, or instance modified ([PTC FAMILY_INFO](https://support.ptc.com/help/creo/creo_pma/r7.0/usascii/model_analysis/modelcheck/checks/family_info.html)). Creo users ask how to suspend verification because it is slow ([PTC Community](https://community.ptc.com/3d-part-assembly-design-327/suspend-family-table-verification-temporarily-128122)). SolidWorks documents that "for each configuration that you activate, the file size of the model increases, as does the time required to rebuild and save" ([SW Help 2019](https://help.solidworks.com/2019/English/SolidWorks/sldworks/c_Managing_Configuration_Data_Help.htm)). Excel-coupled tables add hangs and "swelling" files ([3DSwym](https://3dswym.3dexperience.3ds.com/post/solidworks-user-forum/soliworks-freeze-after-design-table-update_6GALy5iARf6lw-FgsilUkA); [Visiativ forum](https://forum.mycad.visiativ.com/t/fichiers-excell-qui-enflent/97922)) and add-in registration failures in NX ([Siemens KB PL8668524](https://support.sw.siemens.com/en-US/okba/PL8668524/Object-library-not-registerederror-on-part-family-spreadsheet/index.html)). One NX user calls the newer embedded table "way faster than NX+Excel" ([Eng-Tips](https://www.eng-tips.com/threads/nx2306-family-parts-_issues.520695)).

### Wren's text format turns bloat and merge into strengths

Two of the sharpest complaints are things Wren's architecture already avoids, as long as M3.7 doesn't undo it. SolidWorks bloat comes from storing per-configuration geometry in the file. PLAN §8A.1 forbids derived geometry in source files, so a Wren configuration costs only its sparse overrides on disk. Per-configuration meshes and BREPs belong in the regenerable `.wren/` cache. The regen engine already caches features by a hash of their definition plus their inputs (PLAN §4). If the hash covers *resolved* values, switching between configurations becomes a cache hit with no new mechanism, and a background "rebuild all configurations" pass is just the regen engine run per configuration on idle. This is Creo's verify-plus-accelerator done automatically and off the main thread.

Merge is the larger opportunity. Onshape merges at feature-list level. Users report refused merges and copy-paste workarounds ([Onshape forum 3557](https://forum.onshape.com/discussion/3557/merging-branches-with-different-part-studio-versions); [Onshape forum 7302](https://forum.onshape.com/discussion/7302/merge-one-part-studio)), and Onshape's own guide notes that a part deleted in the target stays deleted whatever the source edits were ([Onshape Tech Tip](https://www.onshape.com/es/resource-center/tech-tips/tech-tip-a-guide-to-successful-merging-in-onshape)). **No tool in the evidence merges configuration tables at cell granularity.** PLAN M3.7's per-(configuration, parameter) conflict would be a genuine differentiator, provided configuration identity is an id, not a name. Renaming a configuration on one branch and editing its cells on another must merge cleanly.

### The praised workflows configure in place and choose by value

Users praise configuring **in place**. Onshape's configure mode puts a yellow banner across the workspace and highlights configurable fields on hover. One click adds a column, a field already configured is outlined and blocked from double use, and double-clicking a table cell reopens the feature with that parameter highlighted ([Onshape Help](https://cad.onshape.com/help/Content/PartStudio/part_studio_and_assembly_configurations.htm)). "Configurations are much better implemented in Onshape," says one comparison commenter ([Onshape forum](https://forum.onshape.com/discussion/comment/125960)). SolidWorks marks overrides in yellow in its grid ([SW Help 2020](https://help.solidworks.com/2020/English/SolidWorks/sldworks/r_modify_configurations_dialog.htm)), and Fusion highlights configured items in the timeline and browser ([Fusion Help](https://help.autodesk.com/cloudhelp/ENU/Fusion-Configurations/files/CFG-OVERVIEW.htm)). Onshape tables accept spreadsheet paste and create the extra rows ([Onshape Help](https://cad.onshape.com/help/Content/configurations.htm)), which keeps the ease of spreadsheets without making Excel the source of truth.

As configuration counts grow, every mature tool adds a way to **choose a configuration by its values instead of its name**. SolidWorks built Configuration Publisher because "finding the correct configuration can be difficult if the list is long or the configuration names are not descriptive enough" ([SW Help 2020](https://help.solidworks.com/2020/English/solidworks/sldworks/c_configuration_publisher_top.htm)). Onshape's insert dialog sets inputs and generates a preview ([Onshape Help](https://cad.onshape.com/help/Content/PartStudio/part_studio_and_assembly_configurations.htm)). For M3.7 this argues only for a searchable switcher. Picking a configuration by value at insert time belongs with M6 instances.

The research found **no competitor offering a thumbnail gallery of every configuration at once**. A worker-rendered preview strip is therefore a cheap differentiator, though no evidence yet shows that users want it.

On devices, Onshape lets users create and edit configurations only in the browser; its iOS and Android apps can view and switch ([Onshape Help](https://cad.onshape.com/help/Content/PartStudio/part_studio_and_assembly_configurations.htm)). Wren's phone shell already allows parameter editing (PLAN §9.1). Switching configurations and editing an existing cell on the phone would beat Onshape without bringing the full grid to a phone-sized screen.

## Drawings fail users through silent wrongness, drift and modal friction

### Every tool shares one view grammar

Every mature drawing module follows the same sequence. The user places a sheet, drops a base view from a palette of orientations, projects child views that stay aligned to the parent, then adds dimensions, either imported from the model or placed with an inferring tool, and finally tables and notes. SolidWorks offers a drag-out view palette and resellers recommend importing model dimensions ([CADimensions](https://www.cadimensions.com/?p=3822); [GoEngineer](https://www.goengineer.com/blog/inserting-model-dimensions-into-solidworks-drawing)). Onshape keeps projected views aligned and offers "Break alignment" and "Restore alignment" ([Onshape forum](https://forum.onshape.com/discussion/11225/drawing-problem-with-the-position-of-the-projected-views)). Shapr3D's 2023 overhaul made tapping a base view open a visual menu of aligned projections, and added a settings sidebar for ISO/ANSI, projection, decimals and line widths ([Shapr3D](https://www.shapr3d.com/content-library/an-overview-of-the-2d-drawings-overhaul-whats-done-and-whats-to-come)). Wren should adopt this sequence unchanged. Its novelty budget belongs in propagation, flagging and touch.

The tools diverge on where dimensions come from. SolidWorks reuses modelling dimensions (Model Items), and those are bidirectional: changing an inserted driving dimension in the drawing changes the model ([SW Help 2017](https://help.solidworks.com/2017/english/SolidWorks/sldworks/c_Inserting_Dimensions_into_Drawings.htm)). Onshape staff long told users that sketch dimensions cannot be inserted and must be recreated ([Onshape forum](https://forum.onshape.com/discussion/3774/use-sketch-and-model-dimensions-in-2d-drawing)). An Autodesk staffer justified Fusion's auto-dimensioning work by noting that modelling dimensions are rarely the ones needed for manufacture ([Autodesk forum](https://forums.autodesk.com/t5/fusion-design-validate-document/there-should-be-an-auto-2d-drawing-dimensioning-function-in/m-p/7060359)). NX takes a third path: author PMI in the model and inherit it into views ([Siemens KB PL8010291](https://support.sw.siemens.com/en-US/okba/PL8010291/How-to-display-inherited-PMI-dimensions-in-a-view-with-a-View-Break/index.html)). Wren's plan, "import model annotations" from M5 PMI structures, starting with feature dimensions, is that third path. It should be designed as **curating model PMI**, not as dumping sketch dimensions. The PLAN should also decide whether drawing dimensions can drive the model. Inline values that accept expressions make driving dimensions tempting, but they turn a drawing edit into a model edit across every configuration that shares the value, which brings back the scope problem from M3.7.

### Dangling and drifting annotations are the defining complaint

The single most durable drawing complaint is annotations that break after a model edit. Users experience three grades of failure.

The best is **flagged**. SolidWorks colours dangling dimensions ([Solid Solutions](https://solidsolutions.co.uk/Blog/2023/03/Why-are-SOLIDWORKS-Dimensions-Yellow)), but users still write "Cant select them or do anything! Extremely annoying!" ([3DSwym](https://3dswym.3dexperience.3ds.com/question/solidworks-user-forum/how-do-i-delete-dangling-dimensions_Z2OptDEQSymUQhiYH96XsA)) and ask how to *find* them in large drawings ([Eng-Tips](https://eng-tips.com/threads/how-do-i-find-dangling-dimensions-in-a-large-drawing-document.368638)). SolidWorks only added right-click Reattach in 2024, and **not for imported, DimXpert, chain or path-length dimensions** ([SW 2024 What's New](https://help.solidworks.com/2024/English/WhatsNew/c_wn2024_drawings_reattach_dangling_dimensions.htm)). The #1 idea on the user-voted SOLIDWORKS 2023 Top Ten List was auto-solving dangling relations and dimensions, especially in drawings ([EngineersRule](https://www.engineersrule.com/the-votes-are-in-the-top-ten-requests-from-3dexperience-world-2023/)).

The middle grade is **expected breakage**. FreeCAD's own documentation tells users to add TechDraw dimensions only once the model is finished, because of topological naming ([FreeCAD wiki](https://wiki.freecad.org/Topological_naming_problem/en)). It does offer a Dimension Repair tool that sometimes proposes a fix ([FreeCAD wiki](https://wiki.freecad.org/Translations:TechDraw_DimensionRepair/7/en)).

The worst grade is **silently wrong**. Fusion users report that "most of the dimension references are lost" after updates and that the software "will happily give you an incorrect dimension" ([Autodesk forum 13699550](https://forums.autodesk.com/t5/fusion-design-validate-document/dimensions-on-drawings-loose-reference-automatic-hole-callouts/m-p/13699550); [Autodesk forum](https://forums.autodesk.com/t5/fusion-support/drawing-dimensions-are-incorrect/m-p/12021471)).

Wren's persistent naming and its "never silently guess" rule put it on the right side of this spectrum by construction. The evidence adds four requirements. A dangling annotation must **never display its old value as if it were valid**. Reattach must work for **every** annotation type, including imported PMI, ordinate and chain dimensions. The suggested candidate may be highlighted, as in FreeCAD, but must be confirmed. And the "needs attention" list must be a persistent panel that can be searched and that names the upstream feature, because finding the broken items is itself a complaint.

The second associativity failure is **layout drift**. Even when references survive, placements scatter. A Creo user reports that after minor 3D edits "all the dimensions offset the original position runs too far away, very hard to cleanup" ([PTC Community](https://community.ptc.com/3d-part-assembly-design-327/creo-drawing-dimension-issue-21805)). A 2026 vendor essay argues that any engineering change "scrambles the layout" of PMI-projected views ([Encube](https://www.getencube.com/post/the-drawing-is-not-the-problem)). NX shows a subtler version: inherited PMI extension-line overhang scales with view scale, so a 30 mm overhang at 1:20 becomes 600 mm "by default" ([Siemens KB PL8010408](https://support.sw.siemens.com/en-US/okba/PL8010408/PMI-dimension-extension-line-overhang-is-too-long-in-Drafting/index.html)), and PMI text font and size aren't inherited at all ([Siemens KB PL8003868](https://support.sw.siemens.com/en-US/okba/PL8003868/PMI-Text-Font-and-Size-not-Inherited-from-Model-on-to-2D-Drawing/index.html)). Two rules follow. Placement must be stored as **intent** (an offset from the referenced geometry and a snap lane, both in sheet mm), not as absolute sheet coordinates. And all annotation styling (gaps, overshoots, arrowheads, text heights) must be expressed **in sheet mm, independent of view scale**. Wren's sketch dimension geometry already uses a 1 mm gap and a 1.5 mm overshoot (`docs/DECISIONS.md` ADR-055) and can become the drawing package's ISO style default.

### Click count, overlaps and modal templates are the daily tax

The tedium complaints are vivid and long-lived. A Creo thread is titled "Why I have to do 1200 clicks in Drafting to perform actions that require 1-click in AutoCAD?". It complains that a section line can't be edited without recreating the section view, and it drew a February 2026 reply: "11 years later. PTC is still worthless" ([PTC Community](https://community.ptc.com/3d-part-assembly-design-327/why-creo-drafting-and-annotation-are-so-terrible-why-i-have-to-do-1200-clicks-in-drafting-to-perform-actions-that-require-1-click-in-autocad-why-i-cannot-edit-stupid-section-line-in-annotation-and-have-to-re-create-section-view-why-i-have-to-run-m-49951)). Imported SolidWorks dimensions "come in at odd locations and are not aligned", and the workaround is to import only dimensions "marked for drawing" ([Javelin](https://www.javelin-tech.com/blog/2012/09/cleanly-inserting-key-dimensions-to-a-drawing/)). Shapr3D's 2021 launch users found manual text placement "very tedious" ([Shapr3D Discourse](https://discourse.shapr3d.com/t/ipad-4-0-2d-drawings-are-finally-here/11729)); Shapr3D then shipped dimension snapping with auto-centred labels ([Shapr3D support 5.420](https://support.shapr3d.com/hc/en-us/articles/9671864574364)). Onshape users found that a parent view's rotation couldn't change once dependent views existed ([Onshape forum](https://forum.onshape.com/discussion/11492/drawing-views)).

Vendors now treat overlap as a first-class problem. Onshape auto-breaks crossing extension lines and propagates a hole-callout edit to every instance and to the hole table ([Onshape What's New 2022](https://www.onshape.com/en/resource-center/what-is-new/fillets-hole-callouts-tables)). SolidWorks 2026 adds breaks around dimension text that update when the text moves, and extends its alignment rails to notes, GD&T and surface-finish symbols ([GoEngineer](https://www.goengineer.com/blog/solidworks-2026-drawings-whats-new)). The praised features are "propagate once" and "align for me" mechanics. Neither needs AI, and Wren is well placed for propagation: `HoleFeature` already stores standard, kind, size, fit, counterbore, countersink and thread as structured fields (`packages/contracts/src/document.ts`), so hole callouts and hole tables can be generated from data rather than parsed from text.

Template friction is the third tax. SolidWorks edits sheet formats in a separate mode. Users get stuck in it, can't delete revision rows, see title blocks vanish after editing an imported format, and can't push template changes to existing drawings ([SW forum 187668](https://forum.solidworks.com/thread/187668); [SW forum 78107](https://forum.solidworks.com/thread/78107); [Eng-Tips](https://www.eng-tips.com/threads/reload-border.152505)). Expert advice is to drive title blocks from properties rather than let users edit them ([Eng-Tips](https://eng-tips.com/threads/blocks-and-templates-again.291341)). SolidWorks 2026's new "Display Expressions", which reveals the links behind title-block notes ([GoEngineer](https://www.goengineer.com/blog/solidworks-2026-drawings-whats-new)), shows that opaque links were themselves a pain point. Wren's no-modal rule and its project manifest point the same way: title-block fields are bound properties edited inline on the sheet, the binding is visible on hover, and "re-apply template" works on existing drawings.

### Automation earns trust only when it is inspectable

The 2024–2026 differentiator is automation layered on the shared grammar. Fusion's Drawing Automation and Auto Dimension offer named strategies (baseline, chain, ordinate, overall, symmetric), a datum corner, a density slider, and **alternate positions** to pick from when a single auto dimension is clicked. Auto dimensions never alter manual ones ([Fusion Help](https://help.autodesk.com/cloudhelp/ENU/Fusion-Drawing/files/DWG-AUTO-DIMENSION.htm)). SolidWorks 2026 adds AI "AutoGenerate Drawing", described as beta and later moved into an AI Labs app ([GoEngineer](https://www.goengineer.com/blog/solidworks-2026-drawings-whats-new); [Hawk Ridge](https://hawkridgesys.com/blog/upgrading-solidworks-2026-new-features)). Output quality is still the weak point. Fusion automation produced a stray "0" dimension that Autodesk QA investigated ([Autodesk forum](https://forums.autodesk.com/t5/fusion-design-validate-document/a-bug-and-an-inconsistency/m-p/12685525)), and PMI projection "produces cluttered output" ([Encube](https://www.getencube.com/post/the-drawing-is-not-the-problem)). No independent evaluation of SolidWorks' AI output was found.

The position this evidence supports is that **M4 should ship deterministic, inspectable placement aids (snap lanes, auto-breaks, propagation, "tidy" against explicit lanes) and defer auto-dimensioning to P2**. When auto-dimensioning does arrive, it should copy Fusion's strategy, density and alternates, not a one-shot opaque layout. The counter-argument is that SolidWorks and Fusion now market automation as the headline, so a free tool without it looks behind. But Wren's certification suite (§12A) requires every specified dimension with the right value. A mis-placed auto dimension costs one drag. A wrong or missing one fails the test, and it fails the user's trust in the same way a stale value does.

### Touch splits into snap-heavy authoring and anchored review

Only Shapr3D credibly authors drawings on a tablet. Its winning interactions are snap-heavy: the tap-to-project menu, dimensions that snap to fixed distances, and a double-tap to add tolerances ([Shapr3D](https://www.shapr3d.com/content-library/an-overview-of-the-2d-drawings-overhaul-whats-done-and-whats-to-come)). Its early users complained most about free placement ([Shapr3D Discourse](https://discourse.shapr3d.com/t/ipad-4-0-2d-drawings-are-finally-here/11729)). Onshape documents the best review flow. The comment tool captures a screenshot, the reviewer marks it up with a stylus ("feels like writing on paper"), the markup is saved to a version-pinned comment, and it is assigned as a task ([Onshape tech tip](https://www.onshape.com/en/resource-center/tech-tips/redline-drawing-tablet-paperless)). For Wren, the tablet should author through tap-to-place views, snap lanes and the inline keypad, while the phone should view, measure and mark up. One inference goes beyond the evidence: Onshape's screenshot markup doesn't stay attached to geometry. Markup anchored to drawing coordinates, a version and, where possible, an annotation id would survive revisions. Wren's comments and sharing are P2 because they need Cloudflare (PLAN §2.6), so local-first markup stored as a drawing-layer annotation in the project file is the path that works now. That is an owner decision.

## Configurations and drawings meet at the view, the BOM and the file name

M3.7 was moved ahead of M4 "so both can be built configuration-aware" (PLAN M3.7), and the evidence shows exactly where the seam tears. Every major tool lets a view reference a configuration. Onshape lets users change a view's configuration at any time, and projected views follow their parent ([Onshape Help](https://cad.onshape.com/help/Content/Drawing/view_context_menu.htm)). But in Onshape **the drawing BOM can point at a different configuration from the views** and has to be changed separately ([Onshape forum 22792](https://forum.onshape.com/discussion/22792/drawing-bom-and-view-linked-to-different-assembly-configurations)). The usual workaround is one drawing per configuration, made by copying the tab and changing the reference ([Onshape Tech Tip](https://www.onshape.com/ja/resource-center/tech-tips/how-to-create-an-onshape-drawing-using-configurations)). The design that follows has four parts. A drawing has a **drawing-level configuration**. Views, tables and title-block fields inherit it. A per-view override is allowed and visibly badged. And any view or table that disagrees with the drawing's configuration is listed in "needs attention" as a possible mismatch, though not as an error. "Duplicate this drawing for configuration X" should be a single action, because users take that route anyway.

Fusion shows the more ambitious endpoint: **tabulated drawings**. A configuration table placed on the sheet fills itself, the user chooses and orders the columns, and a dimension can be right-clicked and "replaced with configured aspect" so that one view stands for many sizes ([Fusion Help](https://help.autodesk.com/cloudhelp/ENU/Fusion-Drawing/files/DWG-CREATE-TABULATED-DWG.htm)). Users ask for it explicitly ([Autodesk forum](https://forums.autodesk.com/t5/fusion-design-validate-document/fusion-configuration-display-table/m-p/13629599)). Wren's configuration table already has a parameters-by-configurations shape, so a tabulated drawing needs only a table annotation bound to that data plus a "show parameter name" option on dimension text. This is the strongest argument for the BOM-scope recommendation later in the report: a **part properties table** in M4 that can list configurations is the same table engine.

Part numbers connect configurations to BOMs and files. In SolidWorks, grouped configurations show only user-specified part numbers, and giving every configuration the same `$PARTNUMBER` stops them being listed separately, so **part-number policy directly decides BOM grouping** ([SW Help 2020](https://help.solidworks.com/2020/English/solidworks/sldworks/c_Bill_of_Materials_Multiple_Configurations.htm)). Onshape makes part numbers configurable ([Onshape Help](https://cad.onshape.com/help/Content/PartStudio/part_studio_and_assembly_configurations.htm)). Wren should treat part number and description as ordinary configurable properties in M3.7, use them for "export all configurations, one file each" (falling back to the configuration name, with collisions flagged rather than overwritten), and bind them to title blocks in M4. No vendor documentation of batch per-configuration STEP export was found. SolidWorks users reportedly rely on macros, but that claim is unsourced, which makes Wren's planned one-file-per-configuration export a small differentiator.

## Standards turn the sheet into a parametric template

### Projection, lines and text are document-level settings in millimetres

ISO 5456-2 defaults to first-angle projection and ASME Y14.3 to third-angle. The only difference is where projected views go: in third angle the top view sits above the front view, and in first angle below it ([Xometry](https://xometry.pro/en/articles/first-angle-third-angle-projection/)). Onshape ties projection to the sheet format, so users are surprised when views show "the opposite side" and can't find a separate setting ([Onshape forum](https://forum.onshape.com/discussion/11492/drawing-views)). Projection should therefore be an **explicit drawing property**, defaulted from the standard but independently switchable, and it should drive view placement, the title-block symbol and a check in the certification E2E. Secondary sources describe the truncated-cone symbols inconsistently ([Eng-Tips](https://www.eng-tips.com/threads/request-for-recommended-approaches-for-determining-projection-type-in-engineering-drawings.518366/page-2)), so the symbol must be drawn from the standard's figure and sized from the drawing's text height, which is how ASME Y14.3 sizes it according to forum readings ([Eng-Tips](https://eng-tips.com/threads/request-for-recommended-approaches-for-determining-projection-type-in-engineering-drawings.518366/latest)).

Line widths come from a fixed series. ISO 128-20 gives 0.13, 0.18, 0.25, 0.35, 0.5, 0.7, 1, 1.4 and 2 mm, each step about √2 ([ISO 128-20 sample](https://cdn.standards.iteh.ai/samples/1408/f62555427b87436eafe1e6abc5271860/ISO-128-20-1996.pdf)), and mechanical drawings normally use two widths in a 1:2 ratio ([ISO 128-24 sample](https://cdn.standards.iteh.ai/samples/29095/b2e50c3f669649ae9387373c7a73346d/ISO-128-24-1999.pdf)). FreeCAD ships thick/thin "line groups" of 0.25/0.13, 0.35/0.18, 0.5/0.25 and 0.7/0.35 ([FreeCAD LineGroup.csv mirror](https://huggingface.co/AbdulElahGwaith/FreeCAD/blob/main/src/Mod/TechDraw/LineGroup/LineGroup.csv)). Forum readings of ASME Y14.2 give about 0.6 mm thick, 0.3 mm thin and lettering of at least 3 mm, though the readings disagree on what the 0.3 mm applies to ([Eng-Tips](https://www.eng-tips.com/threads/asme-y14-2.497711)). Y14.2 says these widths exist to tell thick from thin and are "not values influencing acceptance or rejection of drawings" ([Machinery's Handbook](https://online.flippingbook.com/view/954192180/684)). The data model is therefore a named line group plus a role (thick, thin, extra-thick), converted to mm by one renderer that PDF, SVG and DXF all share. ISO 3098 text heights follow 1.8, 2.5, 3.5, 5, 7, 10, 14 and 20 mm ([Roymech](https://www.roymech.co.uk/Useful_Tables/Drawing/Lettering.html)), with stroke width h/10 for the preferred type B ([ISO 3098-0 sample](https://cdn.standards.iteh.ai/samples/24792/1811286881f24ea49763a66a747029c8/ISO-3098-0-1997.pdf)). Defaults of 3.5 mm (ISO) or 3 mm (ASME), with 5–7 mm view labels, fit both standards.

Wren needs a self-hosted drawing font that looks like ISO 3098 type B and contains Ø, ±, °, ⌴ (counterbore, U+2334), ⌵ and ↧. FreeCAD uses Osifont (GPL-3 with a font exception). Its licence and provenance were **not verified** and must be recorded in `docs/DEPENDENCIES.md` before it ships.

### Sheets and title blocks are a function of size, orientation and standard

ISO 5457 sets a 20 mm left filing margin and 10 mm on the other sides. Its four centring marks are 0.7 mm lines with a 1 mm tolerance. The grid-reference fields are 50 mm, measured from the centring marks, with 0.35 mm lines and 3.5 mm characters, and the letters I and O are excluded. That gives 24/16 fields on A0, 16/12 on A1, 12/8 on A2, 8/6 on A3 and 6/4 on A4. Trimming marks are two overlapping 10 × 5 mm rectangles ([ISO 5457 PDF](https://forums.autodesk.com/autodesk/attachments/autodesk/v1232/48404/1/ISO5457.pdf); [cadsetterout](https://cadsetterout.com/drawing-standards/grid-reference-frame/)). ISO 7200 makes the legal owner and an identification number of at most 16 characters mandatory ([ISO 7200 sample](https://cdn.standards.iteh.ai/samples/35446/d3b0887cb4fa47f49f8718807d3b8903/ISO-7200-2004.pdf)). ASME Y14.1 sheets run from A (8.5 × 11 in) to E (34 × 44 in), and their aspect ratios alternate between 1.294 and 1.545, unlike ISO's constant 1:√2 ([Wikipedia](https://en.wikipedia.org/wiki/ANSI/ASME_Y14.1)). A template should therefore be generated, not drawn: `(sheetSize, orientation, standard) → frame, zones, centring and trim marks, title-block anchor`, with a title-block layout whose slots bind to the project manifest. Those slots cover part number, revision (from releases, PLAN §8A.3), material, mass, scale, projection, units, general-tolerance standard, and drawing standard and edition. Grid zones are also needed for the revision table's zone column and for messages such as "dimension in C4 needs attention". ASME Y14.1 margins, zones and title-block layout were not retrieved, nor was ISO 7200's full mandatory field list.

### Dimensioning and GD&T need standard-aware validation, not conversion

Tolerances need display modes for symmetric ±, deviation, limits, basic (boxed), reference (parenthesised) and ISO 286 fits. Hole callouts use the depth symbol (a downward arrow) and the spotface symbol (the counterbore symbol with "SF" inside) ([open-exam-prep](https://open-exam-prep.com/study-guides/asme-gdtp-technologist/ch1/dimensioning-features)). ISO adopted the counterbore, countersink and depth symbols later than ASME, so current ISO usage needs checking ([Eng-Tips](https://www.eng-tips.com/threads/iso-dimensioning.204922)). One GD&T engine can serve both standards, but the legal symbol sets differ. **ASME Y14.5-2018 removed concentricity and symmetry**; in its words these "past practices" are "no longer supported" ([Mitutoyo/Salsbury](https://www.mitutoyo.com/webfoo/wp-content/uploads/ASME_Y14.5-2018_Salsbury.pdf)). ISO keeps both ([ZEISS](https://qualityforum.zeiss.com/migration/images/4532_930ba93a0701c87923e28fa613cdd758.pdf)). ISO 1101:2017 added modifiers such as CZ and SIM, and the standards default differently on simultaneous requirements, though sources conflict on SIM's status ([Knowt](https://knowt.com/note/27d0c404-c3fa-4653-9a4e-3d7f71a4385a/Functional-Equivalence-of-ISO-GPS-and-AS); [Eng-Tips](https://www.eng-tips.com/threads/iso-simultaneous-requirement-1998-vs-2016.438749)). The feature control frame should therefore carry its standard and edition. Validation should **refuse** a symbol that is illegal under the drawing's declared standard, with an explanation, rather than silently converting it. Shapr3D users' complaint that the tool "currently lacks Geometric Dimensioning and Tolerancing (GD&T) symbols" and is "still missing Datum feature" ([Shapr3D Discourse](https://discourse.shapr3d.com/t/gd-t-drawings/13526)) shows why datum feature symbols must ship alongside frames in M4. Exact ISO 129-1 and ASME Y14.5 figures (extension-line gaps, arrow ratios, aligned vs unidirectional text, trailing-zero rules) and the ASME Rule #1 vs ISO 8015 independency default were **not retrieved**. These are standard drafting knowledge but need a licensed copy before the presets are frozen.

### Surface finish moved to ISO 21920; welds and BOMs can wait

ISO 21920-1:2021 cancelled and replaced ISO 1302:2002, and changed the default tolerance acceptance rule from 16% to max ([iTeh](https://iteh.es/catalog/standards/iso/ab03b9a1-0a17-4c24-8163-b4ed7798032e/iso-21920-1-2021); [Quality Magazine](https://www.qualitymag.com/articles/98952-evolving-roughness-standards-understanding-and-implementing-iso-21920)). Both SolidWorks 2026 and Onshape 1.219 added ISO 21920 symbols ([GoEngineer](https://www.goengineer.com/blog/solidworks-2026-drawings-whats-new); [Onshape changelog](https://www.onshape.com/en/changelog/)). An "Ra 1.6" from an old drawing therefore doesn't mean quite the same as one under ISO 21920. The surface-finish annotation should carry a `standard` field (ISO 21920-1 by default, with ISO 1302 as legacy and ASME Y14.36) and show it.

Weld symbols (AWS A2.4 / ISO 2553) are a large separate system. Wren's M4 targets are machined parts, and sheet metal is a v1 non-goal (PLAN §1), so they should stay P2, with the leader and annotation framework left open for them. **No usable source on ISO 6433 balloons or ASME Y14.34 parts lists was found**. That is low risk while M4 needs only a "BOM placeholder", but they need research before M6.

## Exact 1:1 output depends on millimetres end to end

### PDF: the MediaBox, one conversion and a ruler

Printing at the wrong scale is usually the reader's fault rather than the file's. PDF readers default to "Fit to page" or "Shrink oversized pages", and Acrobat has been reported shrinking output to about 98% ([Bluebeam](https://support.bluebeam.com/revu/troubleshooting/pdf-isnt-to-scale-when-printing-from-autocad.html); [Adobe community](https://community.adobe.com/t5/acrobat-discussions/my-pdf-does-not-print-out-to-scale/m-p/12451934)). The PDF fix is `/ViewerPreferences << /PrintScaling /None >>` ([DevExpress](https://docs.devexpress.com/OfficeFileAPI/DevExpress.Pdf.PdfViewerPreferences.PrintScaling); [iText KB](https://kb.itextpdf.com/itext/how-to-prevent-the-resizing-of-pages-in-pdf)). From Acrobat 8 on, the key is reportedly ignored without `/Enforce [/PrintScaling]` ([PDFsharp forum](https://forum.pdfsharp.net/viewtopic.php?p=4369)), and PDF.js historically didn't honour it at all ([Bugzilla 1243580](https://bugzilla.mozilla.org/show_bug.cgi?id=1243580)).

Wren's recipe has four parts. The page MediaBox equals the sheet exactly (A3 is 297 × 420 mm = 841.89 × 1190.55 pt), and the ISO 5457 borders sit inside it. Millimetres convert to points exactly once (× 72/25.4), with **no px stage**. Both the PrintScaling and Enforce keys are written, which probably needs a pdf-lib post-processing pass because jsPDF doesn't expose them. And because the flag can't be trusted, a **100 mm scale bar** and the drawing scale are printed in the margin, and the export panel tells the user to print at "Actual size".

The M4 "measured" acceptance test then has two halves. An automated half parses the PDF and asserts the MediaBox, a known line's length in pt and the line widths: a 0.35 mm line is 0.992 pt, and zero-width hairlines are avoided because they print differently on each device. A human half measures a printed bracket drawing with a ruler on the M2 device-checklist hardware.

jsPDF, svg2pdf.js, pdf-lib and PDFKit are all MIT-licensed. svg2pdf.js "supports only a limited part of the SVG specification" and needs fonts registered in jsPDF first ([svg2pdf.js](https://github.com/yWorks/svg2pdf.js); [jsPDF licence](https://docs.oracle.com/cd/F58861_01/license-oas/jspdf-license-oasli.html)). Wren's drawing SVG must therefore be authored in that subset from day one: presentation attributes, no CSS-only styling, no `vector-effect`, no filters. A golden test should round-trip every annotation type. Whether svg2pdf handles `stroke-dasharray`, markers and `clipPath`, which line types and arrows depend on, was not verified. PDF/A-1 forbids optional-content layers ([Nutrient](https://www.nutrient.io/guides/web/layers/introduction-to-ocg-layers/)), and neither jsPDF nor pdf-lib documents OCG or PDF/A support, so per-role layers and archival PDF/A belong in the open decisions.

Fonts must be embedded. Missing PDF text usually comes from non-embedded fonts ([Autodesk KB](https://knowledge.autodesk.com/support/autocad/troubleshooting/caas/sfdcarticles/sfdcarticles/Error-DWF-created-by-Vault-Job-Processor-has-incorrect-Fonts.html)). Embedding a TrueType subset keeps dimension values searchable and copyable, and outlined text should be an option, not the default.

### SVG: one user unit per millimetre

The SVG fix is one line: `width="420mm" height="297mm" viewBox="0 0 420 297"`, so that one user unit is one millimetre ([W3C SVG 2](https://w3c.github.io/svgwg/svg2-draft/coords.html); [Inkscape wiki](https://wiki.inkscape.org/wiki/Units_In_Inkscape)). Unitless SVG is read as px at 96 per inch, while older Inkscape used 90 and Illustrator 84, which produces the classic 90/96 and 84/96 scale errors ([Inkscape-devel](https://lists.inkscape.org/hyperkitty/list/inkscape-devel@lists.inkscape.org/message/SFR6N36AH5PUYARKZYPFO5OPQKBKIYFD)). Because Wren's drawing editor is an SVG DOM (PLAN §3), it should use sheet mm as its user unit **in the editor itself**. Export then reduces to serialisation and font handling, and svg2pdf receives mm directly. Two text modes cover the two audiences: "editable", with `<text>` and an embedded font subset, for documentation, and "outlined", with text as `<path>`, for fabrication. How laser software such as LightBurn reads SVG units and text was not researched, and it matters because many Wren users will cut from SVG rather than DXF.

### DXF: R2000 by default plus an R12 lines-and-arcs profile

In practice, users report that "DXF files do not contain units" ([comakingspace wiki](https://wiki.comakingspace.de/DXF)), so `$INSUNITS` must always be written (4 for mm, 1 for inches). `$MEASUREMENT` is independent of it and selects linetype and hatch files ([ezdxf docs](https://ezdxf.readthedocs.io/en/stable/concepts/units.html)). Splines are the main cause of laser and CAM rejection. Shops rejected SolidWorks DXFs "even if I export as v2000", and the fix was splines as polylines ([GrabCAD](https://grabcad.com/groups/solidworks-tutorials-on-demand/discussions/best-way-to-export-dxf-for-cnc-lasercut)). Fusion's fit-point and higher-degree splines go missing or warp in Corel, RDWorks and SolidWorks ([Autodesk forum](https://forums.autodesk.com/t5/fusion-design-validate-document/fusion-curves-vs-dxf-curves/m-p/12765864)). Rhino's laser guide recommends "R12 Natural" and prefers tangent arcs to plain polylines ([McNeel wiki](https://wiki.mcneel.com/rhino/exporttolaser)). Version support varies by machine, from software that reads nothing newer than R12 to software that needs 2007 ([Autodesk ArtCAM forum](https://forums.autodesk.com/t5/artcam-forum/laser-dxf-postprocessor-issue/m-p/6895221); [MaxCut](https://feedback.maxcutsoftware.com/p/support-export-to-older-dxf-versions-JLFdYJ)). SPLINE needs R2000 ([ezdxf](https://ezdxf.readthedocs.io/en/stable/dxfentities/spline.html)), and LWPOLYLINE arrived in R14 ([Inkscape forum](https://inkscape.org/forums/beyond/export-to-dxf-r14-lwpolyline-producing-splines)). A LibreCAD user lost every hatch when saving to R12 ([LibreCAD forum](https://forum.librecad.org/Unable-to-save-hatches-to-DXF-R12-tp5720643.html)), and LibreCAD hatches fail when a boundary isn't exactly closed ([Launchpad 1653707](https://bugs.launchpad.net/bugs/1653707)). LightBurn imports MTEXT dimension text horizontally and reads hatches only from R12/R13 ([LightBurn forum](https://forum.lightburnsoftware.com/t/dxf-import-text-dimensions-hatch/58263)).

That evidence supports two profiles and two geometry modes. The **default profile** is AC1015 (R2000), with one layer per line role (visible, hidden, centre, phantom, section hatch, dimensions, annotation, title block). Each layer has an explicit LTYPE whose dash lengths come from ISO 128-20 multiples and a lineweight in 1/100 mm, with `$LTSCALE = 1`, so nothing depends on acad.lin. Dimensions are exploded into lines, filled arrowheads and TEXT, because native DIMENSION entities need anonymous blocks and render differently in each application. The **CNC-safe profile** writes only LINE, ARC, CIRCLE, POLYLINE and TEXT. Splines and ellipses are flattened to biarcs or polylines within a user tolerance (0.01 mm by default; the cleanup advice is at most 0.1 mm for production ([lapas](https://lapas-landing.pages.dev/blog/dxf-problems-troubleshooting/))), and hatches, annotation layers and duplicate or overlapping geometry are dropped. That the ELLIPSE entity needs R13 comes from general knowledge, not a fetched source. The two geometry modes are "sheet as printed" (sheet mm, views pre-scaled) and "true-size part geometry" (one view at 1:1), because laser users want the part, not the sheet. Symbols map to `%%c`, `%%d` and `%%p` where supported. Whether LibreCAD and QCAD render those codes was **not verified**, and ⌴ ⌵ ↧ should be exploded to geometry.

These choices matter more for Wren than for a generic tool. M3.5 made sketch B-splines and elliptic arcs exact OCCT curves (ADR-056), so HLR of any part with a spline or ellipse produces exactly the entities CAM tools reject. The flattening path is not an edge case.

The PLAN's candidate writer, `@tarikjabiri/dxf`, is MIT and TypeScript, but its npm and jsDelivr versions disagree (2.8.9 vs 2.10.0), and a third-party health score reports July 2023 as its last update ([npm](https://npmjs.com/package/@tarikjabiri/dxf); [depscope](https://depscope.dev/pkg/npm/@tarikjabiri/dxf)). The CNC-safe profile's vocabulary is so small that a minimal in-house writer for it is low-risk whatever is chosen for R2000.

### CI can prove "opens in LibreCAD" but not "opens in QCAD" without a licence

The M4 criterion "opens correctly in LibreCAD and QCAD" can't be fully automated for free. **QCAD's `dwg2pdf`, `dwg2svg` and `dwg2bmp` ship only with QCAD Professional**, a commercial product, although they do run headless with `-platform offscreen` ([QCAD command line tools](https://qcad.org/en/qcad-command-line-tools)). One thread reports lines missing from `dwg2pdf` output on 3.23.3 Pro ([QCAD forum](https://www.qcad.org/rsforum/viewtopic.php?p=49248)). Whether QCAD Community Edition has any headless path was not established. LibreCAD's `dxf2pdf` is free and takes paper size, scale and margin flags ([LibreCAD docs](https://docs.librecad.org/en/latest/guides/console-tool.html)), but it needs a display (so Xvfb in CI), and users report empty or mostly blank PDFs depending on the flags ([LibreCAD forum](https://forum.librecad.org/dxf2pdf-output-is-mostly-empty-tp5725553.html)). ezdxf (MIT, Python) offers `doc.audit()` and a recovering reader that reports structural errors with approximate line numbers ([ezdxf recover/audit](https://ezdxf.readthedocs.io/en/stable/drawing/recover.html)).

A credible CI pipeline therefore has four layers, each catching a different class of failure. First, golden tests in Vitest check per-layer entity counts, per-layer total line and arc length, the bounding box in mm and `$INSUNITS`, mirroring the kernel's volume, area and face-count goldens. Second, a pinned ezdxf audit runs with `python -I`. Third, `xvfb-run librecad dxf2pdf` checks that the file renders and that page extents and path counts roughly match Wren's own PDF, with the known flakiness handled by asserting a non-empty, correctly sized page rather than pixel equality. Fourth, QCAD is checked manually before each release, with the result recorded in a validation log in the same way M5 records PMI results in `docs/PMI_VALIDATION.md`. This makes the QCAD half of the criterion a release gate rather than a per-commit check. That is a real weakening, and the owner should approve it explicitly.

## Conclusion

The research changes the framing of both milestones. They are less about feature breadth than about **trust contracts**. A configuration table is trustworthy when every cell says whether it is inherited, and when every consumer (view, BOM, export, instance) holds a configuration id that is flagged rather than defaulted when it goes missing. A drawing is trustworthy when every number on it is either live or visibly broken. Wren's persistent naming, sparse text format, worker regen cache and cell-level structural merge mean it can honour both contracts more cheaply than the incumbents can retrofit them. SolidWorks needed until 2024 to add reattach and still excludes four dimension types. Onshape still merges at feature-list level. An Autodesk forum moderator said in 2023 that Fusion configurations need a commercial or educational licence and a Team hub ([Autodesk forum](https://forums.autodesk.com/t5/fusion-support/new-configurations-feature-missing/m-p/12322886)). The novelty Wren can afford is in propagation, per-configuration status, merge and anchored markup, not in AI layout.

Two risks remain unpriced. Most of the standards figures above come from secondary sources and iTeh previews, so templates, line types and GD&T presets need a licensed-standards check before they are frozen into goldens. And the "opens in QCAD" criterion can't run in free CI. Both are cheap to settle now and expensive to discover in a release.
