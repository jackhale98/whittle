# Put the pivot and the commands under the cursor

Across SolidWorks, Creo, NX, Fusion, Onshape, FreeCAD, Rhino and tablet CAD, users praise the same thing: **the tool comes to the cursor**. That means shortcut bars and radial menus that open where the pointer is, flick gestures, repeat-last, pick-from-list for overlapping geometry, and an orbit that turns about the point being looked at. They complain about the reverse: **errors reported far from their cause**, pop-ups that lag and catch a mis-click, truncated or shifting context menus, UI churn, licence and offline lockouts, and navigation conventions that differ from tool to tool. Wren's orbit "feels off" for a concrete reason. It turns about a stale fit-centre target that pan and dolly-to-cursor drag into empty space, with no visible pivot, on the left button that every other tool keeps for selection. PLAN §3 picked camera-controls for "orbit-around-cursor", but `packages/viewport/src/viewport.ts` never turns that on. The fixes are cheap and well evidenced: pivot on the raycast hit under the cursor, fall back to the visible-model centre, show a marker during the drag, move orbit off the left button, drop drag smoothing, and ship navigation presets. Three live patents need counsel before Wren copies more. **Wren's current view cube matches the abstract of the active ViewCube patent (until about 6 Mar 2029). Cursor-pivot orbit sits near the SteeringWheels patent (until about 3 Mar 2030). The branch-and-merge already shipped in M2.5 sits near Onshape's patent (until about 24 Feb 2036).** The core marking-menu patents have expired, so radial and flick menus are open to Wren.

## Users reward cursor-local commands and punish errors reported far from their cause

The most consistent complaint across the desktop tools is about **where a failure is reported**, more than the failure itself. The #1 idea on the user-voted SOLIDWORKS 2023 Top Ten List was auto-repairing dangling relations and dimensions. #5 was "Tell Us Which File Is at Fault" ([EngineersRule](https://www.engineersrule.com/the-votes-are-in-the-top-ten-requests-from-3dexperience-world-2023/)). Fusion users say its timeline warning "Constraints were removed" is "not enough information to trace back what I may have broken" ([Autodesk forum](https://forums.autodesk.com/t5/fusion-support-forum/timeline-is-frustrating-unintuitive-and-at-times-unusable/td-p/11869353)). The UIST 2024 DeCAD paper gives the mechanism: CAD systems **highlight the operation that failed, not the earlier operation that changed the reference**, which leaves the user debugging a broken program ([DeCAD paper](https://obikate.github.io/papers/decad.pdf)). FreeCAD 1.0 reduced topological-naming breakage, but a commenter showed that deleting an earlier chamfer still broke a later one ([Hackaday](https://hackaday.com/2024/11/20/freecad-version-1-0-released)). Wren's "needs attention" rule already refuses to guess. The evidence says it should also **name the upstream feature whose output changed**, not only the downstream feature that failed.

The sketcher has its own version of this problem, and it affects Wren directly because Wren uses the same solver family as FreeCAD. FreeCAD reports conflicts by constraint index, such as "Over-constrained: (#, #, #)" ([FreeCAD wiki](https://wiki.freecad.org/Sketcher_SelectConflictingConstraints)). Its solver "does not have a preference, so it just selects one of the redundant constraints", so the flagged constraint is often not the one the user just added ([FreeCAD tracker](https://tracker.freecad.org/view.php?id=3976)). One blogger got "Redundant constraints: (61)" with no way to understand why ([New Screwdriver](https://newscrewdriver.com/2023/09/07/freecad-notes-midpoint)). Wren should translate planegcs output into a highlighted conflict set on the canvas and in the list, propose the most recently added constraint as the one to remove, and never show a bare number.

Blocking and lag come next. SolidWorks users complain that menus open slowly and that the single-threaded rebuild stops them working elsewhere ([r/cad mirror](https://redlib.nohost.network/r/cad/comments/1di59xk/biggest_issues_with_solidworks)). The sharpest lesson comes from the 2009 SolidWorks context toolbar. When it appeared late, users clicked "on something 'behind' the menu" and accidentally suppressed features ([3DSwym](https://3dswym.3dexperience.3ds.com/post/solidworks-user-forum/who-else-hates-the-left-click-pop-up-menu_0eLbRZLgSEyXF4-T8uhSOg)). Wren's worker kernel already removes the blocking rebuild. The remaining risk is the context bubble: it must never appear under the next click.

Menu design draws the same verdict in every tool. SolidWorks right-click menus open truncated behind a chevron ([SolidWorks 2015 What's New](https://help.solidworks.com/2015/English/WhatsNew/c_shortcut_menu_enhancements.htm)). Creo's right-click options depend on the active ribbon tab ([PTC Community](https://community.ptc.com/t5/3D-Part-Assembly-Design/WF5-Drawing-ribbon-Menus/m-p/406175)). A FreeCAD core developer counted **28 top-level commands** in the tree context menu for one Part object ([GitHub #13194](https://github.com/FreeCAD/FreeCAD/issues/13194)). An Onshape user says a long right-click menu "starts to slow me down" ([Onshape forum](https://forum.onshape.com/discussion/comment/107626)). Context menus should be short because they are curated, not because they are cut off.

Trust failures last longer than UI failures. Fusion caps offline work at two weeks ([Autodesk help](https://help.autodesk.com/cloudhelp/ENU/Fusion-Designs/files/ASM-FUSION-OFFLINE-MODE.htm)). Its 2020 personal-use change cut hobbyists to 10 editable documents ([Autodesk support](https://autodesk.com/support/technical/article/Fusion-360-Free-License-Changes)). Onshape's free plan has allowed only public documents since 2016 ([Fabbaloo](https://www.fabbaloo.com/2016/11/onshape-switches-up-subscription-options-unlimited-docs-pushes-for-pro)). SolidWorks users fight 3DEXPERIENCE named-user login failures ([Visiativ](https://visiativ.co.uk/news-resources/common-3dexperience-connection-challenges/)). Fusion's toolbar redesign drew "fix the bugs first" backlash, and the opt-out was only temporary ([Autodesk IdeaStation](https://forums.autodesk.com/t5/fusion-360-ideastation-archived/new-ui-hard-to-read/idc-p/8974418)). Wren is local-first, GPL and needs no account, so it wins this category by default. It keeps the win only if command locations stay stable and file operations work offline.

The praised mechanisms all share one shape. The table below condenses them; the sources are cited in the sections that follow.

| Tool | Most-praised efficiency mechanisms | Most-cited complaints |
|---|---|---|
| SolidWorks | S-key shortcut bar at the cursor, right-drag gestures (2–12 directions), D-key breadcrumbs, Select Other, drag handles | Errors far from cause, truncated right-click menus, single-threaded blocking, 3DEXPERIENCE login |
| Creo | Mini toolbar on click, Smart selection filter, mapkeys | Ribbon travel, tab-dependent menus, model "spins off screen" |
| NX | Command Finder (teaches location), 3 + 1 radial menus, Selection Intent, QuickPick hold-to-list, selection bar with per-command memory | Radial menu regressed from flick to hover, remembered state catches users out |
| Fusion | Right-click marking menu with flick and Repeat, searchable S-key toolbox | Opaque timeline errors, RAM and crashes on long histories, 14-day offline cap, toolbar churn, repeat not key-bindable |
| Onshape | Branch/merge with compare, no-save, Follow Mode, navigation presets, Select Other, keymap conflict flags | Browser steals keys and right-click, free plan public-only, wheel step too large |
| FreeCAD | Python echo of every action, spreadsheet-driven parameters, 1.0 smart Dimension and on-view values, 1.1 Clarify Selection | Workbench sprawl, TNP, index-only solver messages, 28-item menus, many navigation styles |
| Rhino | Right-click repeat, typed values mid-drag, object snaps with tracking lines, aliases, popup toolbars | Right-click repeat surprises newcomers, unstable overlap-menu order, view "whips off screen" |
| Shapr3D / Onshape mobile | Pen authors and finger navigates, selection-driven tools with drag glyphs, long-press offset reticle, sketch rotation lock | Too many taps, no iPad hardware shortcuts, no Pencil hover highlight, weak mouse support |

The vendors' 2025–2026 changes all move toward Wren's principles. SolidWorks added a Simplified Interface that shows "the most commonly used commands" ([SolidWorks blog](https://blogs.solidworks.com/products/solidworks/whats-new-in-solidworks-2026-design)). Its 2026 release moved the Modify dimension box so that it **no longer covers the dimension**, and added command search that understands "terminology from other CAD software" ([GoEngineer](https://www.goengineer.com/blog/solidworks-2026-ui-ux-performance-and-imports-whats-new); [CAD Software Direct](https://blog.cadsoftwaredirect.com/?p=10051)). Designcenter NX added press-and-drag curve creation alongside click-click, plus gesture-based commands ([Siemens](https://blogs.sw.siemens.com/nx-design/whats-new-in-nx-core-design/)). FreeCAD 1.0 and 1.1 brought a unified Dimension tool, on-view parameters, transparent previews, drag handles and searchable preferences ([Libre Arts](https://librearts.org/2024/11/freecad-1-0/); [FreeCAD 1.1](https://freecad.github.io/Website/download/releases/1-1/)). Wren already starts at the place these products are converging on. It should start minimal and grow, not ship a full command set with a "simple" toggle.

## Right button, radial flicks and pick-from-list decide daily speed

### Radial menus beat linear menus, but only as flicks

The HCI evidence favours radial selection, with one caveat. Pie menus gave shorter seek times and fewer errors than linear menus in Callahan et al. (CHI '88) ([UMIACS](https://sites.umiacs.umd.edu/node/16962)). Co-author Don Hopkins later put the gain at about **15%** ([OSNews](https://www.osnews.com/story/30371/pie-menus-a-30-year-retrospective/)). In Kurtenbach and Buxton's field case study, an expert mark was **3.5× faster** than selecting from the open menu. The study had only two users, and experts still reopened the menu to refresh their memory ([Autodesk Research](https://research.autodesk.com/publications/user-learning-and-performance-with-marking-menus); [Berkeley summary](https://people.eecs.berkeley.edu/~fox/summaries/ui/marking_menus.html)). The design point is that the novice path (wait and look) rehearses the same movement as the expert flick ([Buxton](https://billbuxton.com/PieMenus.html)). The caveat comes from Springboard (CHI 2006): once homing and travel are counted, a local marking menu was not significantly faster than a round trip to a palette ([Microsoft Research](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/Springboard-CHI-2006.pdf)). Wren should measure total selection cost, not menu time alone.

Users notice when a radial menu stops working as a flick. After one NX update, the radial menu required hovering directly over an item instead of moving toward it, and users complained ([Eng-Tips](https://www.eng-tips.com/threads/radial-menu-selection-gestures.460281)). Fusion's marking menu accepts a flick without waiting for the menu to draw, and users flick up for Repeat. They still asked for Repeat on Space or Enter, because "the mouse gesture is inherently slower than being able to have it key-bound" ([Autodesk forum](https://forums.autodesk.com/t5/fusion-design-validate-document/how-to-make-fusion-repeat-last-command-with-space-or-enter-key/m-p/10109414)). PLAN §9.4 already binds Space to repeat. FreeCAD and Rhino users met their demand for pie menus with fragile add-ons. Those add-ons went unmaintained, had a "Context" mode one reviewer called "too ambiguous", grew item lists that were "quite long", and crashed the Rhino 9 WIP ([devtalk](https://devtalk.freecad.org/t/piemenu-v20/64141); [McNeel Discourse](https://discourse.mcneel.com/t/new-rhino-radial-menu-so-good/214192)). Blender's developers keep default pies simple because complexity works "against the speedy, gestural input" ([Blender devtalk](https://devtalk.blender.org/t/pie-menu-development-for-blender/6171/10)). The design follows from this: a native radial menu with **eight or fewer items**, contents chosen by selection type, flick-to-select with a direction-plus-distance threshold, a fixed Repeat slot, and the same layout on every surface.

### The right button needs one coherent mapping

The right button is where conventions collide hardest:

- **SolidWorks:** right-drag runs gestures in 2, 3, 4, 8 or 12 directions. Middle-drag orbits ([SolidWorks Help](https://help.solidworks.com/2023/english/SolidWorks/sldworks/c_mouse_sestures.htm)).
- **Fusion:** right-click opens the marking menu, and middle-drag pans by default ([Autodesk help](https://help.autodesk.com/cloudhelp/ENU/Fusion-GetStarted/files/GUID-6514ABC1-CB75-4F0B-AB0E-316FAD36BA93.htm); [GrabCAD](https://print.grabcad.com/tutorials/activate-orbit-rotate-feature-via-mouse-in-fusion-360--1)).
- **Onshape:** right-drag orbits and middle-drag pans ([Onshape forum](https://forum.onshape.com/discussion/comment/12178)).
- **Rhino:** right-click repeats the last command, right-drag rotates, and press-and-hold opens a popup ([Rhino docs](https://www.rhino3d.com/docs/guides/gestures/)).

Rhino's three-way split is the most efficient pattern found, and the most complained about. One returning user's thread was titled "Arrg — right-click repeats last command, help me make it stop", and they fixed it by setting a 50 ms context-menu delay ([McNeel Discourse](https://discourse.mcneel.com/t/arrg-right-click-repeats-last-command-help-me-make-it-stop/193340)). Other threads complain about the click-versus-drag threshold ([McNeel Discourse](https://discourse.mcneel.com/t/rhino7-right-mouse-button-rotate-vs-enter-sensitivity/143907)). Wren today maps left-drag to rotate, right-drag and middle-drag to pan, and suppresses the browser context menu (`viewport.ts`, `configureControls` and `attachInput`). No surveyed tool orbits on the left button. They keep left for picking and box-select, whose direction convention (left-to-right encloses, right-to-left crosses) is shared by SolidWorks, Onshape and Rhino ([SolidWorks Help](https://help.solidworks.com/2020/English/SolidWorks/sldworks/c_Box_Selection.htm); [Onshape help](https://cad.onshape.com/help/Content/selection.htm?Highlight=box+select)).

Here is the defensible default, an inference that has not been user-tested. It is Onshape-like: left selects and box-selects, right-drag orbits, middle-drag pans, and the wheel zooms to the cursor. A right press released within a few pixels opens the radial context menu. A held key opens the same radial and supports flick-on-release, which gives marking-menu expert speed without taking right-drag back from orbit. Presets cover the alternatives:

- a SolidWorks/NX-like preset: middle-drag orbits, and right-drag becomes flick gestures;
- a Fusion-like preset;
- a Rhino-like preset in which right-click repeats.

Every preset has an independent invert-zoom toggle. Creo users need a config.pro flag to reverse wheel zoom ([PTC KB](https://www.ptc.com/en/support/article/CS133100)) and resort to AutoHotkey to remap the middle button ([PTC Community](https://community.ptc.com/t5/3D-Part-Assembly-Design/Middle-Mouse-button-customization/m-p/222641)). Onshape ships exactly these presets ([Onshape tech tip](https://onshape.com/en/resource-center/tech-tips/tech-tip-changing-rotate-pan-and-zoom)). Shapr3D stores one per input device ([Shapr3D Support](https://support.shapr3d.com/hc/en-us/articles/7873881091356-Navigation-Presets)). FreeCAD is the counter-example: it offers a dozen styles and admits Mac combinations "do not work as expected", because none of its developers owns a Mac ([FreeCAD Manual](https://wiki.freecad.org/Manual:Navigating_in_the_3D_View)). Wren should ship **one strong default and a few named-by-behaviour presets**, not a style zoo. The evidence on laptop trackpad mapping is thin, so a trackpad preset needs its own test.

### Overlapping geometry needs a deterministic chooser

Every mature tool built a way to pick geometry that overlaps or hides other geometry:

- SolidWorks Select Other lists the items under the pointer and can hide faces ([SolidWorks Help](https://help.solidworks.com/2026/English/SolidWorks/Sldworks/r_select_flyout_menu_general.htm)).
- NX QuickPick lists candidates after a hold of about 0.5 s, and the delay can be removed ([Eng-Tips](https://eng-tips.com/threads/default-selection.368200)).
- Onshape's Select Other is bound to the backtick key, which then failed on Spanish and UK keyboards ([Onshape forum](https://forum.onshape.com/discussion/15847/select-other-not-working)).
- FreeCAD 1.1 added Clarify Selection, which makes nearby geometry transparent ([FreeCAD 1.1](https://freecad.github.io/Website/download/releases/1-1/)).
- Rhino's Selection Menu is criticised because its **order is unpredictable**: the top item did not always select the same surface, and staff could not state the sort rule ([McNeel Discourse](https://discourse.mcneel.com/t/tuning-the-selection-menu-when-selecting-overlapping-geometry-curves-blocks/128836)).

The Bubble Cursor, which always captures exactly one target, significantly beat point cursors and follows Fitts' law ([Grossman & Balakrishnan, CHI 2005](https://www.dgp.toronto.edu/papers/tgrossman_CHI2005.pdf)). That suits tiny edge and vertex targets. Wren's PLAN §9.2 "Which one?" chooser is the right idea. It needs a stable order (nearest to camera, then by type), a hover highlight for each candidate, scroll or Tab cycling, a layout-neutral key, and a long-press equivalent on touch.

### Browser input needs deliberate handling

Onshape's forum is a catalogue of the hazards. Keys are consumed by the browser before the app sees them, Cmd-S opened the browser's save dialog, Alt-Left and Alt-Right collide with back and forward, and Mac users get the browser context menu ([Onshape forum](https://forum.onshape.com/discussion/631/control-key-unavailability-due-to-browser-hijack); [conflict tag](https://forum.onshape.com/discussions/tagged/keyboard-shortcuts-conflict); [right-click on Mac](https://forum.onshape.com/discussion/19068/right-click-stopped-working-on-mac)). Onshape now flags "browser shortcut conflict" in its keymap editor ([Onshape help](https://cad.onshape.com/help/Content/Home/keyboard_shortcuts_and_hotkeys.htm)). Wren should match `event.code` and display layout-aware labels. It should also flag conflicts, keep default bindings off reserved chords, and suppress middle-click autoscroll and the back/forward side buttons over the canvas. Two HCI results set the remaining defaults. ExposeHK, which overlays hotkeys on commands while a modifier is held, raised hotkey use and speed across three studies ([Malacria et al., CHI 2013](https://hal.archives-ouvertes.fr/hal-01894253)). Spring-loaded quasimodes cut mode errors where a latching pedal did not ([Springboard](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/Springboard-CHI-2006.pdf)). Temporary states such as "suppress snapping" should therefore be hold-to-activate, and Esc should always return to neutral selection.

## Wren's orbit feels off for five compounding reasons

Reading `viewport.ts` alongside the research turns "feels off" into a ranked diagnosis. One correction to the brief first: camera-controls applies **0.06 s smoothing while dragging** (`draggingSmoothTime`). The 0.18 s value (`smoothTime`) applies to wheel dolly and programmatic moves. The polar clamp is camera-controls' default stop at the poles. `fitTo` sets the target to the bounds centre.

**First, and most important, the pivot is not where the user is looking.** Wren orbits about the camera target, which is set to the bounds centre at the last fit. In camera-controls, truck (pan) and dolly-to-cursor move that target too, as a side effect, along a plane at the target's depth. This is how the library behaves, and it should be confirmed in a test. After a few pans and zooms toward a detail, the pivot is a point in empty space. Autodesk's Safe 3D Navigation study describes exactly what happens next. If the pivot is off-screen, orbit "has a similar effect as Zoom". If the pivot is beyond the object, orbit acts like pan. Users then said things like "oh, I must have picked zoom by accident" ([Fitzmaurice et al., I3D 2008](https://research.autodesk.com/app/uploads/2023/03/safe-3d-navigation.pdf_recHpo5niNlpDtQQu.pdf)). Users of other tools describe the same failure:

- A Creo user's spin centre seemed "a couple of hundred feet behind my head", and the model slid off screen ([PTC Community](https://community.ptc.com/t5/3D-Part-Assembly-Design/Model-Spins-Off-Screen/m-p/373014)).
- A Rhino 8 user wrote: "NO ONE WANTS THE OBJECT TO WHIP AROUND AND GO OFF SCREEN" ([McNeel Discourse](https://discourse.mcneel.com/t/rotate-about-an-item-in-perspective-tumbles-it-out-of-view-v8/200980)).
- Another Rhino user found the rotation centre "always … (0,0,0)" ([McNeel Discourse](https://discourse.mcneel.com/t/how-can-i-set-a-view-rotation-center-in-rhino-now-the-view-rotation-operation-is-suffering/87727)).
- Fusion, SketchUp and Revit forums carry the same complaint ([Autodesk forum](https://forums.autodesk.com/t5/fusion-design-validate-document/please-fix-the-orbit-pivot-point-behavior-sooner-rather-than/m-p/6203677)).

The tools users like all pick the pivot from the geometry under the cursor:

- Onshape rotates about the geometry under the mouse and falls back to the model centre over empty space ([Onshape forum](https://forum.onshape.com/discussion/comment/12178)).
- SolidWorks uses visible geometry near the view when the model is not fully in view, and highlights the pivot in magenta ([SolidWorks Help](https://help.solidworks.com/2021/English/SolidWorks/sldworks/r_Middle_Mouse_Button.htm)).
- NX places a temporary rotate point on a middle-button hold, with a configurable delay ([MCAD Central](https://www.mcadcentral.com/threads/temporary-rotation-point-in-nx5.26409)).
- Inventor uses the cursor location when the model is outside the view ([Inventor help](https://help.autodesk.com/cloudhelp/2023/ENU/Inventor-WhatsNew/files/GUID-5DF5F44E-5AFB-42E9-B9B5-704D382A31A7.htm)).
- FreeCAD's "Drag at cursor" ray-picks the model point at button press, and was the default through 1.0 ([FreeCAD source](https://github.com/FreeCAD/FreeCAD/blob/main/src/Gui/Navigation/NavigationStyle.cpp)).

**Second, the pivot is invisible.** Safe 3D Navigation added a visible pivot ball that is enlarged and transparent during the drag and hidden afterwards. It "had an immediate positive effect in all of our user tests", and confusion between commands was "eliminated" ([Fitzmaurice et al.](https://research.autodesk.com/app/uploads/2023/03/safe-3d-navigation.pdf_recHpo5niNlpDtQQu.pdf)). SolidWorks highlights the pivot in magenta, Creo shows a spin-centre icon, and FreeCAD shows a rotation-centre sphere by default ([FreeCAD .ui source](https://github.com/FreeCAD/FreeCAD/blob/main/src/Gui/PreferencePages/DlgSettingsNavigation.ui)).

**Third, orbit is on the wrong button.** As the previous section showed, no surveyed desktop tool orbits on left-drag. Muscle memory from every one of them fires the wrong action in Wren, and Wren gives up left-drag box-select in model mode.

**Fourth, the rotation model sits between two camps.** SolidWorks, Creo and NX default to free, trackball-style rotation ([PTC Help](https://support.ptc.com/help/creo/creo_pma/r9.0/usascii/fundamentals/fundamentals/about_orient_types.html)), so MCAD switchers feel a turntable as constrained. Rhino defaults to "Rotate around world axes" ([Rhino 8 Options](https://docs.mcneel.com/rhino/8/help/en-us/options/view.htm)). Onshape added a "default rotation behaviour to constrained rotate" preference after users complained that free orbit "rolls and tilts" ([Onshape forum](https://forum.onshape.com/discussion/4285/can-i-change-the-orbit-mode-to-something-like-sketchup)). The research supports Wren's turntable choice. A fixed up-vector "Fixed Trackball" counts among the predictable controllers ([Bade et al.](https://typeset.io/pdf/usability-comparison-of-mouse-based-interaction-techniques-93urfv7o3m.pdf)), and usability improves when the fixed axis matches the object's intrinsic up axis ([Visual Computer 2021](https://link.springer.com/article/10.1007/s00371-021-02394-x)). Arcball, by contrast, is analysed as inhomogeneous and discontinuous ([Henriksen et al.](https://core.ac.uk/download/269088256.pdf)). FreeCAD's corner-roll "Rounded Arcball" confuses users unless the roll zone is shown ([GitHub #21403](https://github.com/FreeCAD/FreeCAD/issues/21403)). The problem in Wren's version is the **hard polar clamp**. A user rotating to inspect the underside hits a wall, while the MCAD tools let them carry on over the top. Wren should keep turntable as its default and allow continuous rotation over the poles, flipping the up vector when the view inverts. It should make free rotation the default in the SolidWorks-, Creo- and NX-like presets. It should also scale sensitivity by the pivot's screen position, as FreeCAD's `spinInternal` does for off-centre pivots ([FreeCAD source](https://github.com/FreeCAD/FreeCAD/blob/main/src/Gui/Navigation/NavigationStyle.cpp)).

**Fifth, smoothing adds lag to direct manipulation.** No CAD tool surveyed applies orbit inertia by default. FreeCAD ships spin-after-release off, and Rhino documents no inertia setting ([FreeCAD .ui source](https://github.com/FreeCAD/FreeCAD/blob/main/src/Gui/PreferencePages/DlgSettingsNavigation.ui); [Rhino 8 Options](https://docs.mcneel.com/rhino/8/help/en-us/options/view.htm)). A Rhino Mac user complained when OS trackpad momentum kept the view moving for "two or three seconds" ([McNeel Discourse](https://discourse.mcneel.com/t/issue-rotating-view-perspective-following-most-recent-rhino-5-update/2613)). Even 60 ms of drag smoothing makes the model trail the hand. No study quantifies orbit smoothing, so this is an engineering inference. Wren should track 1:1 while the pointer is down and keep the spring presets for fits, standard views and transitions.

The fix follows from the diagnosis. At pointer-down for an orbit, raycast with the existing BVH pick. Pivot on the hit point. On a miss, use the centre of the visible bodies' bounds, never the stale target or the world origin. Show a small pivot marker only during the drag. If the pivot leaves the screen, re-centre it at the same depth. Lock the clicked point under the cursor during pan, as Safe 3D Navigation does. Add explicit pivot gestures: a quick middle-click to set the centre, as FreeCAD's `lookAtPoint` and NX users expect ([FreeCAD source](https://github.com/FreeCAD/FreeCAD/blob/main/src/Gui/Navigation/CADNavigationStyle.cpp); [McNeel Discourse](https://discourse.mcneel.com/t/nine-wish-set-center-of-rotation/221234)), and an optional "orbit about selection". Add arrow-key rotation about screen axes with a configurable step. SolidWorks offers this, with Shift for 90° ([SolidWorks blog](https://blogs.solidworks.com/products/solidworks/how-do-i-manipulate-my-model-view-let-me-count-the-ways/)), and Rhino uses 6° by default ([Rhino 8 Options](https://docs.mcneel.com/rhino/8/help/en-us/options/view.htm)). On touch, the same pivot logic applies to one-finger orbit. Onshape's auto-engaging rotation lock while sketching ([Onshape blog](https://www.onshape.com/en/blog/under-the-hood-cad-for-mobile)) should come along too. One caution: FreeCAD 1.1 switched its default from cursor pivot to window centre, and no rationale was found ([FreeCAD 1.1.0 source](https://github.com/FreeCAD/FreeCAD/blob/1.1.0/src/Gui/PreferencePages/DlgSettingsNavigation.cpp)). Wren should A/B the change under `pnpm perf` and in user sessions rather than assume it.

## WebHID gets Wren most of the way to CAD-mouse support, with no iPad path

The case for 6-DoF devices is real but weakly evidenced. A 3Dconnexion-commissioned Fraunhofer study reports **28% shorter task time** and 29% fewer hand movements in Siemens NX ([Digital Engineering 24/7](https://digitalengineering247.com/article/3d-mice-improve-ergonomics-at-cad-workstations-study-shows)). The research notes disagree on its sample size (14 advanced CAD students in one summary, 24 participants in another), and the vendor promoted the results. Independent work is more mixed. Hinckley et al. found 3D orientation input up to **36% faster** than Virtual Sphere and Arcball for orientation matching ([UIST '97](https://www.microsoft.com/en-us/research/?p=151164)). The Globefish study, however, found an integrated 6-DoF puck compared unfavourably with separated rotation control ([Kulik et al.](https://www.uni-weimar.de/fileadmin/user/fak/medien/professuren/Virtual_Reality/documents/publications/kulik_globefish_small.pdf)). Some Creo power users say the gains come from mapkeys, not hardware ([PTC Community](https://community.ptc.com/t5/Creo-Modeling-Questions/3D-Connexions-3D-Mice/m-p/199839)). Even so, the SolidWorks and NX users Wren wants to attract will expect the device to work.

Browser support is the hard part, and Onshape's users show the failure modes. Its route depends on the vendor's 3DxWare driver and a local bridge. Users hit stale auto-generated certificates and Chrome "Local network access" prompts, and the driver detected "Chrome" rather than the app, which left only basic pan and zoom ([Onshape forum](https://forum.onshape.com/discussion/comment/117140); [Onshape forum](https://forum.onshape.com/discussion/comment/127150)). There are three routes in total:

- **WebHID** works only in desktop Chromium, from Chrome and Edge 89 ([Chrome Developers](https://developer.chrome.com/docs/capabilities/hid)). It receives no reports while 3DxWare holds the device ([3Dconnexion forum](https://forum.3dconnexion.com/viewtopic.php?p=125693)).
- **3DconnexionJS** needs 3DxWare plus a Navigation Proxy, and ships under a proprietary SDK licence rather than an OSS one ([pkgstats](https://www.pkgstats.com/pkg:@3dconnexion/3dconnexionjs)).
- **spacenav-ws** bridges the open-source spacenavd driver on Linux, by reverse-engineering Onshape's client traffic ([PyPI](https://pypi.org/project/spacenav-ws/)).

Safari and iPadOS have no WebHID, so no tablet path exists.

The plan should treat devices as layered, feature-detected adapters behind one navigation input contract. The contract lives in packages/contracts and is lead-owned, so this is a proposal for the lead. The first adapter is WebHID, parsing the HID reports in Wren's own GPL code with the vendor and product IDs kept as plain data. The second is an optional 3DconnexionJS adapter, loaded at runtime from the user's own install and never bundled. Counsel must confirm that this keeps proprietary code out of the GPL bundle and is compatible with the self-hosting rule. The third is a documented localhost WebSocket protocol that a spacenavd bridge can target. A **diagnostic panel** should report which path is live; Onshape's users had to work out silent failures themselves. Device buttons should map in-app to Wren commands: fit, standard views, the radial menu and Repeat. This avoids the vendor's per-app profile detection, and Fusion users still could not customise radial menus through 3DxWare 10.8 ([3Dconnexion forum](https://forum.3dconnexion.com/viewtopic.php?p=76874)). The 6-DoF puck must share the cursor-pivot logic. Creo's spin centre misbehaved with a 3D mouse until the user clicked the model ([PTC Community](https://community.ptc.com/t5/3D-Part-Assembly-Design/Model-Spins-Off-Screen/m-p/373014)), and FreeCAD needed a 2026 fix to "honor rotation center mode for SpaceMouse" ([FreeCAD PRs](https://github.com/FreeCAD/FreeCAD/pulls?q=rotation+center)).

2D CAD mice need less work. The 3Dconnexion CadMouse has a low-force dedicated middle button, a radial-menu button behind the wheel that opens a 4- or 8-segment menu, and "Smart Scroll" with adjustable inertia ([AUGI review](https://augi.com/articles/detail/product-review-3d-connexion-cadmouse); [CadMouse Pro manual](https://media.distrelec.com/Web/Downloads/_m/an/CADMousePro_eng_man.pdf)). The radial button reaches the browser as an ordinary button or keystroke, depending on how the driver is configured. Wren therefore needs any-button binding, including side buttons 3 and 4, to its own radial menu. Its wheel handling must also cope with high-resolution and inertial wheels; Onshape users already complain that each wheel step zooms too far ([Onshape forum](https://forum.onshape.com/discussion/5213/mouse-wheel-scrolls-too-much)).

## Tablets reward a pen-authors, finger-navigates split that a PWA can mostly deliver

Shapr3D's central rule, that **the finger moves the view and the Pencil makes geometry**, is the most-praised pattern in tablet CAD. A DEVELOP3D reviewer said the split "makes complete sense" ([DEVELOP3D](https://develop3d.com/cad/review-shapr3d-ipad-parasoild-modelling/)). Its selection-driven "Adaptive UI" works the same way: the user selects a face, and a glyph says drag out to extrude or in to cut ([Shapr3D blog](https://www.shapr3d.com/blog/refreshing-the-shapr3d-user-interface)). That is the touch form of "bring the tool to the cursor", and it matches Wren's context bubble. Onshape's 2018 mobile research rejected offset selection and a second-finger tap as a click, because both tested poorly. It chose a long-press **offset crosshair with live pre-highlight**, a magnifier and an auto-engaging rotation lock while sketching ([Onshape blog](https://www.onshape.com/en/blog/under-the-hood-cad-for-mobile)). Users still rate the app **3.5/5**. They say selection is "a pain" with "too many inputs", that the iPad app lacks hardware keyboard shortcuts ("N" does nothing), and that Pencil hover highlight is missing ([App Store](https://apps.apple.com/us/app/onshape-3d-cad/id923421284); [mwm.ai mirror](https://mwm.ai/apps/onshape-3d-cad/923421284)). With a mouse attached, left-drag rotates and box-select is impossible ([Onshape forum](https://forum.onshape.com/discussion/20233/how-do-i-make-a-mouse-work-properly-with-ipad-app)).

These gaps are Wren's opportunity. Safari has exposed Pencil hover to the web since 16.1 on hover-capable iPads ([WebKit](https://webkit.org/blog/13399/webkit-features-in-safari-16-1/)), so the hover pre-highlight in PLAN §9.3 can beat Onshape's native app. A PWA receives hardware-keyboard events for free, so the desktop keymap should stay live in the tablet shell. A mouse in the tablet shell should switch to the desktop button map automatically. Pencil double-tap and Pencil Pro squeeze have no web API; a 2024 Apple Developer Forums question asking for them is still unanswered ([Apple forums](https://developer.apple.com/forums/thread/760238)). Wren therefore needs on-screen equivalents. Feather offers two patterns worth borrowing: a draggable "Finger-Pen" toggle, and squeeze-to-switch-temporarily, which Wren would rebuild as a hold-button under the non-dominant thumb ([Feather support](https://support.feather.art/docs/interfaceandgestures/applepencil)). The finger-pen toggle also helps on phones with no pen.

Two lessons concern history and layout. Shapr3D saw load times stretch on very long histories (500–1000+ steps) and added one-click merging of steps ([Shapr3D Community](https://discourse.shapr3d.com/t/improvements-to-parametric-modeling/31577)). Some users found the added parametric history "more confusing" ([App Store](https://apps.apple.com/us/app/shapr-3d-cad-modeling/id1091675654?see-all=reviews&platform=mac)), which supports ADR-015's sketch nesting and argues for collapsing steps. Shapr3D also admitted that its desktop port was "most heavily optimized for touch" and refreshed it for keyboard and mouse ([Shapr3D blog](https://www.shapr3d.com/blog/refreshing-the-shapr3d-user-interface)). Rhino's decade-long split between its Mac and Windows command lines warns against the opposite error ([McNeel Discourse](https://discourse.mcneel.com/t/rhino-wip-feature-command-line-ui-unification/210508)). Wren's separate shells over one shared `toolGroups` definition are the right structure: shells differ, the command model does not. One conflict should be decided explicitly. Onshape maps two-finger tap to the context menu ([Onshape tech tip](https://www.onshape.com/en/resource-center/tech-tips/tech-tip-mastering-gestures-mobile)), while PLAN §9.3 maps it to undo, following creative-app convention. Wren's choice is defensible, but it needs an on-screen undo button, because the gesture cannot be discovered.

## Three live patents and a dozen trademarks bound what Wren can copy

Copyright leaves Wren a wide lane. Lotus v. Borland held that a menu command hierarchy is an uncopyrightable "method of operation" ([Wikipedia](https://en.wikipedia.org/wiki/Lotus_Development_Corp._v._Borland_International,_Inc.)). Apple v. Microsoft denied "patent-like protection" for GUI ideas ([opinion](https://openjurist.org/35/f3d/1435)). Google v. Oracle found that reimplementing an interface so users can reuse their accrued skills was fair use ([Goldman blog](https://blog.ericgoldman.org/archives/2021/04/u-s-supreme-court-upholds-fair-use-in-google-oracle-software-battle-guest-blog-post.htm)). Navigation and shortcut presets that are "familiar to users of X" are therefore low-risk. That is an inference, because no case addresses shortcut maps directly. Icons, help text, artwork and pixel-close screen clones are ordinary protected expression. Wren must draw its own, with its own packages/ui tokens.

Patents are the binding constraint. In every case below, only abstracts and descriptions were read; **no claims were read**.

## Conclusion

The research turns a vague "feel" problem into a short list of mechanical causes. The deepest is that the plan promised orbit-around-cursor and the code shipped orbit-around-a-remembered-point. Every tool users like treats the cursor as the locus of intent, for picking, commanding and pivoting alike. A Wren that does this consistently across mouse, 6-DoF puck, finger and Pencil would beat Onshape's mobile app, which users still fault for selection effort and missing hover. Wren's structural advantages (a worker kernel, local-first files, no account and GPL) already answer the most durable complaints about blocking rebuilds, offline time-bombs and free-tier rug-pulls. The remaining gap is low-level input polish, and it is mostly configuration and small amounts of code.

The less comfortable finding is that Wren's IP exposure is in work already done, not work still planned. The view cube and M2.5 branch/merge both shipped before anyone read the claims of patents that are live until 2029 and 2036. Neither finding implies infringement, since only abstracts were read. Both should go to counsel before the next public release, and the view cube already has an easy design-around. The evidence gaps are real: there are no controlled studies of orbit smoothing, turntable versus trackball preference, or touch picking error in parametric CAD, and the 6-DoF productivity numbers are vendor-funded. Wren's metrics harness could produce the first public data on several of these questions.
